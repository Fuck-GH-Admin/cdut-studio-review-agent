# N1–N7 补完后的实际复查

日期：2026-10-04。代码基线：`fix/ci-gate-and-version-sync` / `c2f4d901`，electron `0.15.118`、shared `0.1.56`。本报告包含本轮尚未提交的修复。协作者的 [N1–N7 进度记录](2026-10-05-n1-n7-progress.md) 使用 10 月 5 日标题；本文按本次环境日期记录。

## 1. 结论

**这一轮增加了共享契约、政策发布、聚合事务、技术节点、模板向导和批次面板，但尚未完成通用审核 Agent 的本地业务闭环。** 老的三栏预审样例可以操作；新 V2 案卷创建后没有任务，也没有上传、提交和运行入口。模板、批次、评委和离线交接仍有本地实现缺口。

不能沿用“本地可完成部分全部落地，只剩真实环境验证”的结论。真实学校身份、API 与回写需要校方条件；**Pi 执行器实现、OCR 适配、补件回流、独立评分和离线回复应用是本地应完成的代码**，不能归入校方或目标机的外部条件。

本轮已修复能独立定位的界面、定稿、覆盖、分数明细和检查点恢复错误。剩余事项在第 4 节列出，未因单元测试通过而标记完成。下一轮应先走通真实的 V2 单案，再验六模板、批次和独立副本。

## 3. 本轮已修复

### F01 重复挂载与工作页布局

`ContentReviewView.tsx` 的 `PaneWrapper` 原来为每栏都追加三个管理面板，导致三套创建按钮、重复 ID 和旧输入并存。现在使用 Jotai 的 `reviewWorkspaceSectionAtom` 切换“预审工作台 / V2 案卷 / 模板编排 / 批次管理”，管理面板只挂载一次；工作页切换时保留表单。

这改善了布局，没有把 V1 和 V2 数据自动合并。顶部部分动作及助手仍使用 V1 上下文，后续统一工作台时必须一起接入。

### F02 批次过早定稿、快照与重开刷新

- `finalizeBatch` 拒绝空批次及 queued/running/failed/paused 等未完成案卷，UI 同步禁用定稿。
- 定稿前保存完整快照，新增读取并核对 hash 的函数；此前只存 hash，不能还原当时名单与分数。
- 已定稿的同一快照可重试；修改快照要求重开，避免静默把不同快照当成已保存。
- 刷新、定稿、重开使用当前批次 ID，避免 R2 刷新返回 R1。

**剩余限制：** “全部 done”只是最低门控；尚未核验真实案卷/模板政策存在性、评分人数、名额和冲突，批次队列也未启动。不能将此修复记为 U09 完成。

### F03 错误的“全部符合”

`combineCoverage` 现在拒绝已登记未读材料、不符合项、零检查计划以及全 N/A 计划宣称“全部符合”。新增反例测试。

**剩余限制：** 分组检查仍未按真实 `CheckPlanEntry` 展开；V2 运行的 coverage 也未由产物更新。这是函数层修复，不代表用户结果页已经获得完整覆盖判断。

### F04 max 聚合明细重复计分

候选分数 6、3，max 聚合总额为 6，但旧明细会分配 6+3=9。已让分配余额以实际总额为准，保证这一反例中明细合计与总额一致。

精确小数、缺去重键、跨组计划及其他评分合同仍应按 R05 补齐。

### F05 节点检查点未增量保存、缺产物恢复失效

旧代码保存产物后，把原 pending 检查点原样写回；实际续跑又直接把 done 节点标记完成，没有核验产物。

现在先保存产物，再保存 done/waiting/failed 检查点，之后广播节点事件。续跑校验输入指纹、产物版本、所属运行/节点和依赖指纹；失效节点及其下游重做。指定新运行 ID 时复制可复用产物并保留完整检查点。

实际服务探查修复前：后续 parse 执行时，register 检查点仍 pending；删除 OCR 产物后，续跑 OCR 调用 0 次、新运行无产物。修复后：register 已 done 且有 outputRef；OCR 调用 1 次，新运行产物可读。另有指纹损坏重做回归。

**剩余限制：** 真实执行器、完整输入快照、UI 的停止/恢复入口尚未接通；本轮没有以真实模型在进程强退后验完整 U10。不能把函数恢复修复等同于整项 R03/R04 已完成。

兼容影响：旧 `no-input` 检查点不再满足新指纹，会重新执行；后续接入任务/决定执行器时，必须通过幂等应用命令避免把节点重试变成重复业务动作。

## 4. 仍需补完的问题

这里的 P1 指会造成错误结论、丢回复、错误计分或流程无法继续；P2 指普通用户配置、恢复和使用仍有障碍。两类均属于完整交付范围。

### G01 · P1 · V2 主链路断开（N1/N2，U01/U10）

`V2CasePanel.tsx` 只创建固定样例并修改姓名，创建后的 `documents=[]`、`tasks=[]`、stage=draft。`ensureInitialTask` 无生产调用。`RUN_REVIEW_V2` 只有常量，没有主进程 handler、preload 方法或运行按钮；`runReviewCaseV2`、来源索引和视觉分批函数没有生产接线。

**验收目标：** 从模板列表创建非固定案卷 → 上传真实材料 → 提交 → 一次开始 → 查看同一 V2 案卷的进度/产物/待办 → 重启从列表恢复。V1 必须明确保持兼容或迁移，不能混用两份“当前案卷”。

### G02 · P1 · Pi 执行器没有完成审核（N2，R10）

`pi-review-executor.ts:57` 只有注入式客户端壳：Prompt 含节点 ID/hash，没有案卷材料和规则；工具只被转换成名称，没有注册为实际可调用工具；模型返回 `content` 被丢弃，产物固定为 `observations=[]`/`opinions=[]`。没有真实 Pi 客户端适配和其余技术节点执行器的产品装配。

**验收目标：** 复用现有 Pi runtime 的 review toolProfile，实际读取锁定材料/规则，执行业务工具并保存有效产物；缺数据、格式错误和中止不得以空结果标 done。真实模型质量评测在此实现之后进行。

### G03 · P1 · 字段、事实与绑定不一致（N1/N2，U02/R04）

隔离探查复现：数字 0 被 `updateFields` 存为 text "0"；人工更正为 number 7 后，观察为 7，事项字段仍是 text "0"。`setEvidenceLink` 接受不存在的文档版本和另一事项 ID。

`application-service.ts:100/133/165` 未完成模板字段类型/范围/作用域与目标归属校验。创建时枚举、复合字段等也落到 text；不能只依赖 UI 输入正确。

**验收目标：** 所有写命令共用模板校验与事实解析，0/false/枚举保持类型；计算、报告和界面读取同一有效事实。绑定只指向本案实际文件和事项，人工确认值不能被提取覆盖。完整输入快照应包含实际观察、绑定、解析、政策/规则等依赖，当前运行仍传入空观察/绑定数组。

### G04 · P1 · 补件回流会走到无任务状态（N3，U03）

服务复现：退回补件后，未上传回复即可标 satisfied；案卷返回 reviewing，但开放任务 0、responses 0。旧任务被关闭，新的同阶段任务没有创建。`insufficient` 没有继续计入未满足门控，再次满足其他请求可能提前解除等待。

**验收目标：** 实现提交补件回复的命令与页面，关联新文件版本及请求；第一次模糊件判不足仍可再次回复；所有必要请求满足/明确取消后，生成可处理的阶段任务并重审受影响输入。没有材料而要求豁免时，应是附理由的明确动作，不能冒充材料已满足。

### G05 · P1 · 阶段/事项/申诉含义不完整（N3，U04/U05）

服务复现 student actor 可以推进 system 任务。代码还显示：事项通过始终写 `scope=case`，第一次事项决定后，同 task 的再次决定被统一去重逻辑拒绝；决定引用的 `run@revN` 不是实际运行 ID。申诉维持/更正后 status 仍为 in-review，复核可重复；更正继承原决定 actor；最终投影没有按范围合并。

**验收目标：** 本地工作角色与任务执行者匹配；案卷/事项作用域和轮次正确，多个事项能连续处理；决定绑定实际运行/输入版本。申诉有提交和关闭路径，更正由复核人追加，公开结论按范围解析。本地角色校验与真实校方身份验证分别验收。

### G06 · P1 · 独立评分可以重复计票、缺评被掩盖（N5，U09/R08）

[评分探查](assets/2026-10-04-n-stage-recheck/rating-outbox-probe.json) 复现：

- 两位已分配评委，只重复提交 j1 的同一评分两次，ratings 长度为 2，block 策略仍给总分 4，掩盖 j2 缺评。
- NaN 分数可提交。
- 一维 N/A、一维 4 分、各权重 0.5，总分被算成 2；按 N/A 排除分母，应是 4。
- 没有任何分配和评分，block 策略仍给 0。

`judging-service.ts:63/112` 不验证真实 assignment 及唯一票，缺评用数组长度相减，N/A 仍计入权重总和。最低人数、名额和两种 tieBreaker 未完整实现。

**验收目标：** 每个 assignment 只有一份当前有效评分，版本/案卷/评委/维度对应；有限数字、N/A 与缺评正确；最低有效人数及同分处理完成才可定稿。增加独立评委页面及持久评分命令，不把纯数组函数当评分产品。

### G07 · P1 · 离线包返回“已应用”，实际没有应用（N6，U12/R11）

服务探查导入含新姓名的回复包，返回 accepted/“回复已应用”，原案姓名仍为“测试学生”。`offline-roundtrip.ts:117` 只校验包及写进程内 Map，没有调用补件/评分/案卷命令。清空去重 Map 后，同包再次 accepted；这是模拟内存重置，尚非两个进程的往返验收。

**验收目标：** 独立副本实际填写、带附件返回；主副本校验模板/任务/基准 revision 后，以事务应用回复并持久保存 actionId 回执。重复包跨进程不重复执行，旧包明确冲突。该能力不需要等待学校 API。

### G08 · P1 · outbox 不保证发送前持久化（N6，R11/C01–C04）

延迟端口响应时，磁盘没有 pending 文件；`pushViaOutbox` 在 `await port.push` 之后才写。条目也不含完整载荷，进程中断后不能自主重发；同动作并发无队列。`LocalPackageAdapter` 仍在同调用中导出再自行导入，不能作为另一副本的真实接收回执。

**验收目标：** 发送前保存动作及完整载荷，按 actionId 串行；启动恢复 pending，接收端持久幂等；独立收件和确认后才 accepted。分别验证成功后重放、响应前中断、接收后回执丢失及冲突。

### G09 · P1 · 角色投影没有覆盖意见与匿名信息（N6，R12）

未知字段默认 internal 是有效改进。但 `projectForRole` 把所有决定的 reason 都输出给学生/评委；title/subject.title 也未按匿名策略处理。评委“本人评分”从 dispositions 查找，非 JudgeRating。

**验收目标：** 对字段、标题、公开反馈、内部决定理由、附件、身份映射采用统一输出策略；评委只能看到本人的真实 assignment/rating。报告和离线包共用投影，不能只隐藏页面控件。

### G10 · P2 · 模板向导不能编排用户规则（N4，U08）

实际发布向导没有规则原文上传/输入、条件规则、分值公式、材料复用策略、流程编辑或试跑；固定生成虚构 F1/F2/F3，发布后没有模板库与“使用模板建案”入口。“可替换真实政策”也没有对应 UI。六模板 fixture 可发布不等于安装后六业务能使用。

**验收目标：** 用户提供自己的要求，AI 提出带出处的规则草案，负责人确认；配置字段/槽位/条件/计算/流程/输出，试跑后发布。能从模板库建第七类业务并走完补件与终审，源码不改。

### G11 · P1/P2 · 批次还是演示状态面板（N5，U09）

界面硬编码 `caseIds=['case-rt-1']`，独立 QA 配置中不存在该案卷。没有分案、真实队列启动、失败重试、评委分配和评分操作。服务创建批次不核对实际案卷和发布依赖。修复定稿门控后，该示例会一直 queued，用户无法继续，这是如实暴露缺口。

**验收目标：** 选择真实案卷或分案预览确认，队列调用同一个 V2 执行服务；坏案可重试、其余继续。评分矩阵和定稿由真实结果生成，重开轮次可从列表重新进入。

### G12 · P1/P2 · OCR 和发布自检还只有合同/脚手架（N2/N7）

当前 OCR 实现是 `NullOcrPort`；没有可用的 Tesseract 适配器/worker/语言资源接入。空资源目录的 `resourceCheck` 仍报告 allRequiredAvailable=true：OCR 被标为非必需 deferred，文档解析 available 是硬编码。

`runGoldenSet` 只比较条件树的三值结果，没有读取实际固定材料或运行模型/审核链。真实质量确实要实测，但运行适配器、材料固定集和评测管线先由本地实现。

**验收目标：** 随包提供实际解析/OCR 能力及真实资源探测，暴露缺失和重试；以文件→事实→检查→引用→覆盖→计算的固定集评测。全局协议收敛复用公共层，由对应成员协同；本轮只核查了审核执行器壳，未复验 Agent/学业模块全部通信路径。

### G13 · P2 · 已有数据无法重新进入（N1/N4/N5，U10）

真实 Electron 重启已复现：数据文件保留，V2/批次页面恢复为空，向导未发布草稿丢失。当前案卷选择器只读取 V1。用户知道使用方法，也没有可用入口。

## 6. 下一轮建议领取的任务

1. **统一 V2 当前案卷与可恢复入口（G01/G03/G13）。** 案卷列表、模板选择、真实字段表单、材料登记/版本及提交命令四层接线；明确定义观察和表单字段的有效值。验收从零创建且重启能继续。
2. **接实际材料执行与 Pi（G02/G12）。** 复用已有解析器、模型通道和 Pi review profile，实现全部技术节点；提供真实输入快照和 coverage。验收一份完整符合案、一份冲突案、一份失败案，加真实 12 图末批反例。
3. **完成同案补件到终审（G04/G05）。** 两次补件、事项部分通过、终审拒绝和申诉更正均在 UI 完成；有效结论关联实际运行及轮次。验收 U02–U06/U10。
4. **把同一闭环暴露给模板负责人（G10）。** 自有依据、规则确认、流程与试跑；六模板和空白第七业务逐一实际建案，不只校验 fixture。
5. **再接批次与独立评委（G06/G11）。** 复用单案执行队列，先修唯一票、N/A、缺评/最低人数，再接分配评分页及定稿名单。验收坏案不拖全批、缺评不能定稿、重开恢复正确。
