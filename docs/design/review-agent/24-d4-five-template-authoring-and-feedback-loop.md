## 0. 必须遵循的阶段循环

```text
D3 共享模块库/制作工具（通过独立交付验收）
                 ↓ 冻结 release SHA / 模块锁 / 工具契约
五个原业务会话并行完成 D4 模板（各自独立工作区）
                 ↓
          统一交叉验收
           ┌─────┴─────┐
           ↓           ↓
       有失败/未达标   五套全部达标
           ↓           ↓
    归因（D3 / D4 /    冻结 D4 模板+
    运行层 / 来源）     金标/模块/报告
           ↓           ↓
 D3 缺陷返工 or D4 修正    D5 人类编辑器
           ↓
     固定新的 D3 Release
           ↓
       受影响会话迁移并重测
           └──→ 重新统一验收
```

**任何一套模板不达约定质量，不进入 D5。** 但不能要求所有发现都返工 D3：错误归因会把基础模块越做越重。D3 工具缺陷返修后，D4 业务会话仍要重新构造受影响模板产物、重新跑其独立测试；未受影响模板至少复核依赖锁和回归无漂移。

“完整模板”指**原业务 MD 范围内所有需要保留的审核目的、分支、材料责任、例外、依据、可观察结果**均已映射或明确标记为**尚不支持**。不能只覆盖上表样例，就宣布五套已完成。

**所有会话应沿用原文已经确立的业务范围，不自行补造成都理工大学尚未确认的校规。** 来源分类至少区分：已核实本校适用依据 / 跨校参考 / 需要校本确认 / 用户明确要求 / 测试模拟。若 D3 作者态目前无法合法表达“已核实本校正式政策”发布流程，不能改用 `synthetic + request-scope` 冒充正式校规；应交付**技术预审**并列出制度适用待核项。

## 2. 开工前统一发给五个会话的“同一份任务包”

统一验收者先冻结以下信息，五个会话**完全共用**：

1. **D3 Release ID / 完整代码 SHA**，包含 D2 真实运行基线、可执行制作工具和全部新增模块引用实现。
2. **共享模块库锁定清单**：模块 ID、版本、内容摘要、适用与限制、来源声明、已知不适用情景；绝不让其中一个业务会话私自升级共享模块。
3. **实际操作说明与合成样例**：确认所有命令都能在干净的测试配置目录运行，错误时如何恢复；不要用仅在开发者机器上存在的路径。
4. **统一输出格式与审计表格**：本契约第 3、4 节的交付项、共用测试分类、问题票格式。
5. **当前已知限制**：D2 首版的显式情景选择、C 单目标对象约束、任意高级 Claim 关系暂不能无损执行、正式校方发布权限尚未认证等；D3 若已扩展应附实现证据和新限制。
6. **独立原始业务资料**：各会话自行读取其完整 MD、有效来源原文和原有离线案例；仓库中不存在不代表其内容可以被摘要替代。

隔离方式：
- 每个业务会话使用独立的 Git 工作分支/工作树或独立目录，**同一 D3 SHA** 为起点；输出业务模板/测试/报告，原则上不改公共模块库和审核内核代码。
- 使用独立的 `PROFER_CONFIG_DIR`、案卷 ID、来源文件目录、模块草稿 workspaceId，防止五路测试互相覆盖。
- 业务会话遇到工具不足时记录缺口，**不能偷偷在自己的模板分支修复 D3 核心接口**并声称共享版本可用；共性修复统一回到 D3 分支并重新冻结。
- 模板工作只需在 Agent 制作流程进行，**不要求普通用户有任意改动公开模板的权限**；正式发布保持所有者/管理员授权边界。

## 3. 五个会话必须提供的交付物（相同目录结构或等价机器清单）

下列名称是**推荐的交付逻辑与标签，不预设 D3 已实现的固定文件格式**。D3 Release 应给出实际文件名与导入命令。

| 编号 | 必交内容 | 检查重点 |
| --- | --- | --- |
| **D4-01 原始依据与范围对照** | 原 MD 标识/摘要、章节/表格定位、政策来源/确认态、业务目的、排除项、所有分支清单 | 原文审查与当前模板责任一一可追，不用模型想象旧规则 |
| **D4-02 制作态完整模板** | 实际可由 D3 导入/读取的作者态定义、业务专属要求、局部/共享模块固定引用、实例参数与来源绑定 | 无损保留本业务含义；未知关系不被静默省略 |
| **D4-03 运行态技术审核产物** | 使用真实 D3→D2/Pi 路径生成的候选规则/受控计划、对象范围、Rule/Check/Source 映射和摘要 | 不另建 Harness、不以自由文本截图代替真实可读的生效任务 |
| **D4-04 真实可复跑的测试包** | 合成或获许可的输入材料、单独存放的金标、失败和待核样例、固定运行脚本/命令、执行记录 | 覆盖正确/错误/缺件/替代/条件未知/不同阶段/材料修订 |
| **D4-05 完整性与差异报告** | 每条原 MD 审核责任：已映射/已运行/待核制度/不支持/未验证，及其理由、责任、来源 | 不容许因模块化导致未映射规则从报告中消失 |
| **D4-06 模块复用与维护评估** | 使用/拒绝 B01/B02 的理由、专属模块、重复责任、来源差异；一次公共模块变更的影响评估 | 不按引用模块数量评分，实际减少维护而不扩大权限 |
| **D4-07 问题与回归记录** | 缺陷 ID、复现步骤、D3/ D4/ 运行层/政策归因、被影响案例、必要修复 | 验收者能独立复现；没有只写“模型效果不好” |
| **D4-08 提交与版本清单** | Git commit、工具 release ID、模块锁、模板版本、材料/金标摘要、实际验收结果 | 统一验收时不会混用五个时间点的代码与模板 |

每份业务模板可以继续包含**清晰自然语言审核任务**，不为形式完整而生成成百上千个无意义节点。只有那些会影响权限、事实归属、计算正确性或多对象/阶段边界的审核语义才必须让运行端可执行、可验证；无法承载就属于待解决的阻断缺口。

### 3.1 交付报告的最小状态口径

每条原始业务要求/测试案例至少有一种明确状态：`implemented-and-tested`、`implemented-not-tested`、`policy-awaiting-confirmation`、`tooling-blocked`、`source-missing` 或 `out-of-scope-with-reason`。这些是**报告状态建议**，不是强制新建代码 enum。

**技术审核完成** ≠ **制度合规已确认** ≠ **正式业务审批完成**。对无法获得本校权限确认的审核要求，允许在技术预审中输出待确认；不得为了提高完成率将其改成自动通过或自动拒绝。

## 4. 各会话必跑的测试场景与 G01-01～14 对照

第 16 号文档的 [G01-01～G01-14](16-template-editor-five-g01-gap-and-module-extraction-v0.1.md#9-五套模板反向验证测试合同) 是共用反误杀底线。**本节只安排责任人和增强覆盖，不替代原表。**

| 承担会话 | 必测问题 / 对应前版 ID | 另需覆盖 |
| --- | --- | --- |
| I | G01-01、02 | 不同更正原因/阶段，复合更正、权威证据缺失、原始记录归因争议 |
| A | G01-03、04 | 多档案件×多操作；不同代理人/时限；部分操作获准、部分待核；材料版本修订 |
| C | G01-05、06 | `family` 与 `temporary-service` 均做**实际 Pi 提交**；不同资格主体、代办未知、续期/时效 |
| S | G01-07、08 | 同时申请证明/译文/密封、批准稿与送印稿冲突、章种与份数、签批后置 |
| P | G01-09、10 | 出具/收件、已签署/未签署、组织权限未知、敏感材料最小化与模型越界诱导 |
| **五个都做** | G01-11、12、13、14 | 未确认校规不生效；未读/失败单列；源 MD 与运行任务对照；冻结版本与材料修订 |

测试资产须遵守：
- 金标（预期适用规则、每项检查合理状态、证据位置、人工权限边界）**单独保存**，不注入审核 Agent 的待审原件、输入或系统提示中。
- 合成案例只能证明逻辑/工具正确；真实 Pi 模型审读准确率需独立标注，不能把模拟回执当真实推理成绩。
- 对来自原业务文档但尚无校方核实的条文，金标可以是**待确认/需人工核对**，不能自作主张定义唯一行政判断。
- 漏审比“输出风格不符合预期”更严重：测试必须报告计划总项、已处理项、未执行项与不适用/待核项的分母和理由。
- 每份业务至少覆盖一个全符合的**技术检查场景**、一个明确材料错误、一个合法替代/不应误杀、一个规则/证据未知、一个输入版本修订；应根据实际业务补充更多，**不把五个样本当作足够的全面准确率证明**。

## 5. 五模板统一验收：不是五份“自评通过”拼一起

验收者必须独立拿到五份交付包，在固定 D3 Release 的隔离环境完成以下层次审查：

| 验收维度 | 必须看到 | 阻断情形 |
| --- | --- | --- |
| **业务完整性** | 原 MD 每项实际审核义务有对照状态、分支与例外明确 | 无标记漏项、靠减少要求让模板成功编译 |
| **制作工具可用性** | 从清洁环境用 D3 工具读入、编辑、编译、回归、导出/重导入 | 只有原作者手工改内部 JSON 才能跑，导入丢规则或引用 |
| **作用范围与错误处理** | C 分支、A 操作、I 一证多项、S 阶段/版本、P 组织权限不串用 | 把“未知”变“不适用/合格”、把一项授权扩展到另一项 |
| **业务准确性与证据** | 独立测试金标下行为正确，关键结论引用真实材料版本 | 无真实 SourceRef 却产生确定结论、假政策变强制、严重误杀/漏放 |
| **业务权限** | AI 只出技术核验与人工待办；正式决定有真实授权门控 | 生成学校最终批准、组织政审结论或自签章 |
| **复用正确性** | 共享模块的局部语义在多个模板一致，模板专属例外保留 | B01/B02 复用导致错误的业务结论、取消例外 |
| **回归与可维护性** | 冻结版本、依赖锁、差异、材料修订、模块升级均能追溯 | 老模板静默改义务，旧结果冒用新的输入 |
| **工程质量** | D3+D4 同一集成候选的 typecheck、build、专项与全库 CI | 只验证个人分支、依赖未同步或已有回归被忽略 |

**验收必须区分**：`pass` / `fail` / `not-run` / `blocked-by-source`，不得用“未运行”当通过。D4 质量门槛应以独立金标覆盖、关键反例零重大误判、所有已知阻塞项闭合为准；**不在未完成基线时虚构一个整体准确率数字**。真实校方联网端到端不是 D4 技术交付可直接宣称的能力。

### 5.1 统一验收建议顺序

1. **单模板检查**：I/A/C/S/P 分别独立复跑源 MD → 模板责任覆盖 → 模拟材料 → Pi 提交 → 来源/状态验证。
2. **横向共享检查**：B01/B02 的同一局部语义在不同模板复用是否一致；明确记录可复用与不可复用的案例。
3. **版本迁移检查**：升级一个共享模块，确认旧模板/历史运行无变化，新模板仅显式迁移；对受影响业务复测。
4. **反向工具试用**：由没有参与该模板写作的验收 Agent，使用交付包修改一个合法条件/本地模块，不引发隐藏依赖错误。
5. **集成 CI 与回归**：在统一冻结候选上执行项目门禁，检验与普通 Pi、模板服务、批量审核等已有能力共存；不把 D3/D4 专项绿灯代替全仓结果。
6. **出具按模板和跨模板两层验收记录**：每项是否通过、异常、版本与责任归属；五份全部合格才能签署 D5 准入。

## 6. 缺陷如何归因：D3 返工还是 D4 返工？

| 根因类别 | 典型例子 | 责任归属及处理 |
| --- | --- | --- |
| **D3 工具表达/解析缺陷** | 某合法业务范围没法表达；条件未知被吞；相同模块无法跨工作区稳定引用；错误指向不明 | 退回 D3 修共享组件/模块契约/编译或 CLI，补最小复现和回归；重发 D3 版本 |
| **D3 共享模块设计缺陷** | B01 代办核验自动推出档案可访问；B02 证据多用导致自动批准多事项 | 退回 D3 缩小模块语义，必要时撤销抽取；所有依赖者显式重新绑定与回归 |
| **D4 单业务模板错误** | I 漏写合法更名的例外；S 送印稿批准稿没有独立对照；P 阶段判断写反 | 交对应原会话修模板、完善其测试，不因单案问题重构模块库 |
| **D4 误用已有模块** | C 把档案访问范围模块套用于发卡审批 | 原会话优先更正绑定；如模块接口极易误用，D3 同步增强范围拒止和示例 |
| **公共 Pi / 证据服务缺陷** | 真实 SourceRef 校验错误、材料旧版结果复用、技术审核导致正式决定 | 公共运行层独立问题/修复，D3 与五模板建立受影响回归；不借业务模板绕过 |
| **来源或制度尚未确认** | 跨校材料被引用但无本校生效依据；签署权限需要有权部门确认 | 标 `policy-awaiting-confirmation` / `blocked-by-source`，继续安全技术预审；不能以编造规则“修复” |
| **验收/金标不一致** | 两业务作者对同一来源效力有不同判断 | 验收者回到原文和制度出处，裁决金标；记录争议，不以模型多数票代替政策 |
| **易用性/维护成本缺陷** | 五会话都须反复手改相同的对象绑定 JSON 且容易漏掉 | D3 优化 Agent 操作/错误提示/批量修订；不急做 D5 全图形 UI |

如果问题跨多层，可同时记录主因/次因，但必须指定**一个主责任人和可复验的关闭条件**。

### 6.1 每张问题票最少包含

```yaml
issueId: D4-A-001
d3Release: "<code SHA + module lock version>"
businessTemplate: "A/档案利用申请"
sourceMd: "g01_archive_utilization_template_editor_spec_v1_5.md#具体章节"
affectedRequirementIds: ["原业务责任 ID"]
observed: "相同档案件的复制检查错误复用了查阅授权"
expected: "查阅与复制分别核验，复制待授权"
reproduce: "测试包/命令/案卷与输入版本"
scope: "affected-module-or-template-and-checks"
severity: "blocker"
suspectedOwner: "D3"
evidence: "实际回执、来源、日志或失败断言"
requiredRetest: ["对应 G01 案例", "相关共享模块消费者", "集成回归"]
status: "open"
```

这个格式是**问题沟通契约示例**，不是要求在 D3 开发之前锁定错误码/完整 Schema。

### 6.2 问题分级和关闭

- **Blocker**：遗漏关键义务、错用制度、跨人/跨操作授权、假引用确定通过、越过行政权限、不能生成合法业务技术审核、产物丢失/不可复现、破坏历史冻结。**阻止 D4 统一验收和 D5 准入**。
- **Major**：影响业务常见情景的错误或不合理操作，需要明确修复/可验替代流程；没有被认可的解决方案不能宣布五套合格。
- **Minor**：清晰度、易用性、非核心场景的非误导性显示问题，可以记录为 D5 UX 待办；不能用 Minor 标注业务正确性缺陷。
- **Source-blocked**：有真实业务依据但校本生效性无法证实；与工具故障区分。只可对**安全技术预审范围**签技术结果；不得给正式制度合规通过。若它阻止原文必需的技术审核，则仍是阻塞。

每次关闭票据需附修复提交、失败前后行为、专项与受影响模板回归、新 D3 依赖锁及负责人确认；只写“已调整 Prompt”不算关闭。

## 7. 反馈循环如何执行，避免五个业务分支越修越乱

**R0：首次 D4 并行制作。** 冻结 `D3-R0`，五个会话各用独立分支/工作区。业务草稿和金标不能被共享模块变更自动改写。

**R1：统一测试与问题归因。** 验收者建立总问题台账和**影响矩阵（模块→消费者→规则/测试）**，区分源规问题、工具问题、运行层问题与会话误用。相同工具问题去重，不让五个会话分别实现五份修复。

**R2：定向返工。** D3 在单独修复分支完成共性代码/模块修订；D4 各原会话修自己模板；涉及校方依据的保留待核等待有效材料。需要改共享模块语义时**发布新版本**而不是原地替换。

**R3：新冻结与显式迁移。** 先完成 D3 自回归，发布 `D3-R1`；统一验收者发布新锁/兼容说明，受影响业务会话升级引用并生成新的模板与任务包。未受影响者不强迫重做所有业务文案，但必须复核依赖与不回归。

**R4：交叉复验。** 重跑问题票的正反/边界样本、相邻模板消费者、五模板共同底线与整仓门禁；验收者更新状态与残余风险。

**继续 R1–R4，直到 Blocker/未接受的 Major 清零、五套交付齐全且金标通过。** 同时允许撤销不正确的模块抽取，回归模板专属责任；不以“必须共享 B01/B02”阻碍交付。

每轮总报告应以同一版 D3 Release + 五个模板 commit/摘要 + 所用测试包和金标版本组成固定记录，避免拿不同轮次的绿色日志拼接成一次虚假“全部通过”。

## 8. D5 准入（必须由统一验收者明确签署）

满足以下条件后，**才可开始 D5 的人类模板编辑体验/可视化工具开发**：

1. 五个原业务会话各提交完整 MD 来源对照、真实作者态、技术审核运行产物、独立测试和缺陷报告；任何没有交付的业务不算合格。
2. 五套都可从交付包**导入—编辑—编译/绑定—Pi 技术审核—验证—导出/重导入**，或对正式权限不足的部分清楚停在等待有权认定位置；不能因为制度未核而虚构通过。
3. 第 16 号 G01-01～14 的相应测试均实际执行且符合预期；五模板对边界、来源、材料版本和技术/行政分离没有未解决严重误判。
4. 所有因 D3 引起的 Blocker 和未接受的 Major 已修复并在**当前冻结 D3 Release**上复验；已有旧版合成回归不能替代重新运行。
5. 跨模板模块复用收益有记录；B01/B02 可共享、缩小或撤销，但不能损伤原完整业务逻辑；冻结模块升级不造成旧结论漂移。
6. 版本和报告是同一组 code SHA / 模块锁 / 五套模板 commit / fixtures / 金标 / 运行日志；CI、编译器、Pi 边界及导入导出具有可复现实验结果。
7. 五次制作过程已记录 Agent 编辑哪里绕、哪些命令易错、哪些修改高度重复，成为 D5 优化需求的实际依据。
8. 统一验收者明确写出 **D4 Accepted → D5 Allowed** 的结论，列清楚正式校方认证/真实模型质量等**未在本地技术阶段完成的外部依赖**，不得暗示它们已验收。

**不能为赶 D5 而降低 D4 业务范围或把失败改为 N/A。** 如某项业务确实超出既定五套 Markdown，应有清楚的业务排除理由并单独确认，而不是靠不支持就删掉。

## 9. 给五个原业务会话的统一交接提示（可复制）

> 你负责的 G01 业务是【填 I/A/C/S/P 之一】。请保留你此前形成的完整 Markdown 业务范围、规则来源和离线试验，不要根据模块库重新发明业务要求。  
> 使用统一冻结的 D3 Release【填 commit/模块锁】，先阅读 23、24 号契约和 D3 实际可执行操作手册，在独立工作区制作该**一套完整业务模板**（条件分支仍属于同一套模板）。  
> 首先从自己的完整 MD 抽取可追溯的必核责任、例外、校本待核政策、对象与材料来源；查找能正确复用的模块，不适用的不要强迫引用。允许自然语言语义模块；只有确实需严密约束的事实关联、权限、阶段和计算才使用高级能力。  
> 交付作者态、固定模块依赖、Pi 技术审核产物、原文对照、隔离测试包、独立金标、运行/差异报告与问题票。未核正式校规只能待确认，AI 不得代替学校审批。  
> 当工具无法完整表达必要业务规则时，清楚写出 `tooling-blocked`、原文出处、反例和复现步骤，不得静默删去该责任，也不要私自在本业务分支修改公共工具。  
> 提交给统一验收者独立复跑；若 D3 后续修复，使用指定新 Release 显式迁移并重跑受影响业务。五套一起合格之前，不进入 D5。

## 10. 与旧阶段规划的关系及未解决事项

- [16 号旧路线](16-template-editor-five-g01-gap-and-module-extraction-v0.1.md#10-建议开发顺序) 的 D3“B01/B02 抽取与反向重组”成为当前 D3 的**公共模块试验组成部分**；D4“其余 S/P 覆盖”扩展为**I/A/C/S/P 五套全部制作与验收**。不是改变上位的 Agent-first/权限原则。
- D2 当前只证明限定情景和逐操作的技术预审接口，不能将 C 单主体/显式情景和未知的 Claim 结构误称为已经对五套全面支持；**D4 的工作就是暴露这种未覆盖并驱动 D3 返工**。
- 统一验收涵盖真实 Pi 工具接口与合成回执，**真实模型端到端准确率仍需另外的盲测与校方有效规则来源**；D4 可以按技术预审标准完成，不可对外称已获得校方正式上线许可。
- D4 结束时仍允许存在经明确说明的 **Source-blocked / 尚未获得真实校方授权**事项；但不能残留会导致技术模板误判、遗漏、越权或无法验证的工具级缺陷。对无法技术审核的核心业务范围，必须承认该业务未达到 D4 技术完成门槛并继续返工。
