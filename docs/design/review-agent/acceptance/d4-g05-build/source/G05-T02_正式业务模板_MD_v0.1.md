# G05-T02｜集体校外交流实践活动组织与安全审核——完整业务 Markdown 母版（C v0.1）

> **模板 ID**：`G05-T02` · **成果类型**：独立 C 作者侧业务母版（非部署文件、非软件已验证实现） · **源研究基线**：B v0.2 校本补研（2026-10-12） · **冻结候选**：C v0.1。
>
> 本模板的唯一目的为**校内受权主体拟组织集体校外活动的组织资格、人员与安全材料审核及其有权审批事件核验**。共享字段仅供抽取、检索、建模；不得合并为学术会议资助、三下乡立项、教学实习、财务报销等另一审核目的。所有适用学校/年度/项目的强制条件都必须通过已生效 `policy_profile` 激活；缺校本校规不妨碍通用业务设计，但不允许自作成都理工大学现行规则。

## 2. 独立审批目的、边界及被排除的相邻业务
- **正向**：组织者以一次活动为基本申请单元，请求学校主管单位核验外出组织权限、活动计划、成员、运输、保险、安全预案、承诺和分级有权批准；并对修改、撤销、行前确认、执行异常和返校归档形成可追踪状态。
- **排除**：个人旅游或个人自主服务岗位报名（可转个人实践/S06）；以教学培养方案为目标的课程实习（教学审批由S06/T01承担，是否并行安全检查取本校明文）；社会实践成果立项/奖助/学分（S05/S06）；普通教职工个人出差、学术会议资助（人事/出差/G05-T01）；差旅费、实习费、带队教师报销（财务G07/T04）；高危野外或涉外考察的专门许可（G04/外事专业部门）。
- **负责任的边界**：不因教学实习属他域就声称其完全不需要安全管理；不因三下乡项目立项成功就发组织安全许可；不因差旅事前审批已经存在就推断保卫备案完成。依据 `L02,L07,L10,W01,W02`。
- **混合场景**：同一人/单位可在多个业务申请中重复使用一份真实材料，但每一`approval_purpose`与`decision_id`必须独立；一个人获准参赛不等于某团队获准组织出行。
## 3. 人员、组织、签署与执行的角色图谱
| 稳定角色 | 主体责任 | 不被允许推定为 |
|---|---|---|
| `APPLICANT` 请求人/组织发起人 | 单位负责人、社团负责人或有正式授权的学生团队 | 最终审批者 |
| `AGENT` 经办/委托代理人 | 只按授权动作上传及补件，可与组织者不同 | 默认可以撤销/改签已批准版 |
| `BENEFICIARY_MEMBER` 受活动影响成员 | 每人有独立参团、时段、保险与承诺事实 | 全体都能代表组织签名 |
| `ACADEMIC_ADVISOR` 指导教师 | 学术、思想与项目指导，2025 CDUT专项须按L02验证在职 | 一定全程现场带队/终审 |
| `ON_SITE_LEADER` 实际带队负责人 | 行前清点、现场联络、情况报告 | 当然是审批部门负责人 |
| `SAFETY_CONTACT` 安全联络员 | 预案响应、报告接收链 | 有权批准高危活动继续 |
| `RECEIVING_PARTY` 校外接待方 | 说明愿意接待/某时段场所安排 | 校内审批者 |
| `APPROVING_AUTHORITY` 有权主管部门或领导 | 正式批准、拒绝、变更/撤销，权限由校规配置 | 学生附件或AI模型 |
| `EXECUTION_MANAGER` 现场执行及保险管理人 | 处理实际成员变动和突发事件，并向部门报告 | 自动能够审批新活动版本 |

**签署顺序**必须按`role_scope + activity_version + effective_date`校验；原材料中“老师同意”只证明来源可核的指导意见，不能自动转为部门、保卫或校领导决定。学校真实OA事件优先，是否接受特定电子签与亲笔签由政策profile决定。
## 4. 业务条件轴、分支逻辑、互斥与未知
统一三值 `T/F/U`：`T`有可追溯权威条件事实，`F`有可追溯反事实，`U`缺来源/相冲/接口不可用。触发的`U`绝不能按 `F`走无需材料的宽松路线；也不能按`T`误加外校强制条件。先执行业务归类`BR-01`、加载profile`BR-02`，再应用可叠加安全条件，最后结合动作和阶段确定需审材料。

**组合表达**：`eligible = official_policy_applicable AND authorized_organizer AND qualified_activity_scope`；当任一项是`U`，保留对应待核状态；每个风险/交通/保险分支独立可叠加，`risk=high`优先触发人工安全节点。`BR-01`活动主类型、`BR-02`主profile、`BR-12`单次动作互斥；出行分段交通、夜间住宿、承保、授权与成员身份可同时触发。

**覆盖的B阶段18个场景**：S01—S18（社团、三下乡、集体异地、人数边界、包车、保险、家长知情、课程实习、个人出行、重大变更、审批待形成、已有正式否决、异常、归来）。本模板继续使用独立的`BR`而不新建同目的子模板。

|---|---|---|---|---|

## 5. 输入契约：申报事项、申报材料、证明材料与可信底账
- **申报事项**（结构化请求）：`activity_id`, `requested_action`, `request_version`, `organizer_type`, `applicant_ref`, `intended_start/end`, `requested_outcome`, `affected_member_ids[]`, `related_business_refs[]`。一个申请可包含变更组、成员逐项核验、多个审批节点请求，但每项`review_unit_id`和规则ID独立。
- **申报材料**（申请人/组织方表达）：`M-01`申请表、`M-02`活动及路线方案、`M-03`风险预案、`M-04`变更单、`M-05`撤回申请、`M-13`出行方式、`M-19`住宿/夜间联系。相同文件承载多个槽时用页码坐标映射事实，不索取重复附件。
- **证明材料**（佐证具体事实）：`M-06`名单、`M-07`指导教师资格、`M-08`组织授权、`M-10/11/12`安全教育签署、`M-14/15/16`承运合同资质、`M-17/18`保险、`M-20/21`接待与介绍信，以及阶段产出的执行/返校证明。
- **可信学校数据**：人员/社团/部门权限、项目/险种保单、正式审批及备案、原始批件快照、合作接待方官方状态、合法外部权威预警。每一项必须附`data_owner`, `access_scope`, `issued_at`, `retrieved_at`, `version`, `reference_id`和`failure_state`。无权限不得从学生截图猜测学校真实状态。

**输入对象最小结构**：`event.source_file_sha256`, `source_page`, `bounding_region`, `extractor_confidence`, `claim_origin`, `timestamp`; 一个`source_file_id`可合法链接若干`MS`，但不能跨审批目的复用决定权。

**逐动作对象**：`review_unit_id=(activity_id,request_version,operation_type,target_type,target_id)`；target_type为`ACTIVITY/GROUP/MEMBER/VEHICLE/INSURANCE/APPROVAL_EVENT/INCIDENT`。多个人不同保险状态可各自审阅，**整队“能否实施”由有权人对最终活动快照决定**。

## 8. 审核事实、跨文件关系与版本时间约束
| 事实 ID | 可审事实及连接键 | 必须拒绝的伪推论 |
|---|---|---|
| `AF-01` | `(activity_id,school_id,organizer_id,version)`可唯一指向活动和批件快照 | 活动名称相同就一定为同一次申请 |
| `AF-02` | `org_id + agent_id + delegation_scope + valid_at`证成组织代表权限 | 社团成员/指导教师自动有签批权 |
| `AF-03` | `member_id + join_state + attendance_window + roster_version`逐人核对成员与出入场时间 | 只比对总人数就证明全部成员一致 |
| `AF-04` | `leader_id/advisor_id/safety_contact_id`按不同职责匹配 | 三名角色必须为同一人，或可互相代签 |
| `AF-05` | `route_segments[] + activity_interval + risk_profile`与预案、接待时间、车辆合同一致 | 计划里出现一个地址就证明整条路线安全 |
| `AF-06` | `member_id + insurance_policy_id + coverage_start/end + region`匹配成员时段 | 团体险封面有校章就证明全队均有效承保 |

| `AF-09` | `old_version -> proposed_diff -> new_approval_event`识别人数、路线、交通更正 | 改文件名字即可扩大原批准范围 |
| `AF-10` | `incident_at + affected_ids + source_authority + response_at`记录风险与事故上报 | 安全评估通过就能忽视之后的实时预警 |

**时间语义**：申请、签署、保险起止、活动集合、变更、审批、归来分别记录**时区**；工作日算法须由`school_calendar_id`绑定（节假日、补班）。下界/上界的包含性以当前校规明确配置，不假定所有保险条款精确到秒的同一含义。2025文书不可推定2026活动沿用同一规则。
## 9. R-01—R-46 原子规则（完整执行意义）
规则编号继承B阶段候选`R-01`至`R-46`，C阶段予以完整执行语义。`policy_scope`默认只在`resolved_policy_profile`下触发，其中源标签`L`只证明成都理工大学指定年度专项，`W`仅证明对应外校制度，跨校归纳需标`设计约束`；无当前明文校规的数字阈值与签批链不得被误设为强制。每条执行应先定位`EV-00`，独立保留`true/false/unknown`和不适用结果。

条目中`触发条件`与`目标对象`为可判断的表达；`已核事实`对应源文件/底账与对应EV；“缺失”表示被激活的**适用材料**欠缺，“冲突”表示存在证据不一致，其处理不能合并；“人工/后续”均不构成自动最终批准。
### `R-01` 主体及业务入口
- **政策适用**：`GENERAL_SEMANTIC_WITH_POLICY_GATE`；源`W01,W03`；须先解析`EV-00`适用学校、年度/项目及阶段，非本校生效规定不可直接拒件。
- **审核目标、动作与受影响对象**：申报组织单位真实存在；经办人被授权针对本活动/版本提交；负责人和经办人可不同；目标类型`ORGANIZATION`（按`review_unit_id`定位）；触发：`action∈{首次申请,变更}且代表组织提交`。B研究条件：组织代表发起。
- **生效阶段**：`ST-01`。**需要证据**：`EV-01+EV-02`；优先关联字段`F-04,F-07`、材料`M-08`；同目标合法等价以第7节EV定义为准。
- **判断界限**：组织活动须具有具体组织单位及授权经办；个人未获正式授权不能代表学校或社团。**未满足/冲突处理**：无活动组织主体→缺件；可信底账明确无授权→权限不符；接口不可达→来源待核；若同等官方证据关键字段相冲，输出`DATA_CONFLICT`并附两端原始定位；仅接口故障则`DATA_UNAVAILABLE`，不得判造假。
- **人工复核、后续动作和问题码**：`ISS-AUTH`。组织/社团主管确认代表权，禁止模型代签；必须保留所需补正材料、最小阻断范围、版本关联和授权部门。

- **人工复核、后续动作和问题码**：`ISS-SIGN`。校团委确认渠道适用和补件；必须保留所需补正材料、最小阻断范围、版本关联和授权部门。
- **作者测试线索（不属D金标）**：打印名或合规电子签的边界。

### `R-44` 权限来源
- **政策适用**：`GENERAL_SEMANTIC_WITH_POLICY_GATE`；源`L02,W03`；须先解析`EV-00`适用学校、年度/项目及阶段，非本校生效规定不可直接拒件。
- **审核目标、动作与受影响对象**：指导教师、业务指导单位、校团委/保卫审批角色分别绑定真实职位和权限；目标类型`APPROVAL_EVENT`（按`review_unit_id`定位）；触发：`学生社团/学生团队有指导人与主管批准`。B研究条件：社团学生团队。
- **生效阶段**：`ST-04`。**需要证据**：`EV-02+EV-05+EV-11`；优先关联字段`F-06,F-23,F-46`、材料`关联EV及该事实对应材料槽；无需单独重复上传`；同目标合法等价以第7节EV定义为准。

### `R-46` 隐私分级
- **政策适用**：`GENERAL_SEMANTIC_WITH_POLICY_GATE`；源`L02,W07`；须先解析`EV-00`适用学校、年度/项目及阶段，非本校生效规定不可直接拒件。

## 10. 逐规则分项状态、问题聚合与输出契约
### 10.1 分项结果与主案状态

**一个事项多目标**：同次活动至少有`ACTIVITY`、`MEMBER[]`、`APPROVAL_EVENT[]`维度；每个`R-xx`可分别输出`PASS_FORMAL`、`NOT_APPLICABLE`、`SUPPLEMENT_REQUIRED`、`POLICY_UNKNOWN`、`DATA_UNAVAILABLE`、`DATA_CONFLICT`、`AUTHORITY_MISSING`、`AWAITING_APPROVAL`、`MANUAL_REQUIRED`、`FORMALLY_REJECTED`、`APPROVED_PENDING_ACTION`、`EXECUTION_RECORDED`等。已经有正式批准和成员资料不齐可以同时存在：批准事件不自动失效，**但对变更/当前执行请求仍需阻断**。

**整体汇总不是覆盖分项**：汇总字段`review_summary_status`是当前请求动作的风险聚合结果，另有`official_approval_status`从有权系统原样读取；二者不可互相覆盖。其优先级在执行可行性上为：官方正式否决/撤销或越权 > 高风险需人工/未完成有权审批 > 不确定政策/数据/证据冲突 > 需补正 > 形式审核合格。`NOT_APPLICABLE`不增加故障权重；多个问题全部保留。高危事故始终阻断自动出发结论；无正式批准记录时即使所有材料合格也只得`PASS_FORMAL + AWAITING_APPROVAL`。

**聚合算子**：逐项结果`findings[]`保留全量，`has_release_authority = official_approval_status = 正式批准 ∧ approved_version=current_version ∧ all_required_predeparture_checks=true ∧ no_unresolved_critical_risk`仅描述“可向有权人建议确认行前条件”；**绝不由模型真正写入`REVIEWED_AND_RELEASED`**。如成员甲乙保险匹配、丙漏保，`member_results`两条通过一条缺险、`review_summary_status`仍为不可自动行前放行。

**代码解释表**：
| 状态码 | 业务含义 |
|---|---|
| `PASS_FORMAL` | 当期可自动验证的材料/条件全合格，只代表形式审查可移交；不产生真实批准。 |
| `NOT_APPLICABLE` | 校方权威规则判定该材料/子操作本阶段不适用；不得缺件计入。 |
| `SUPPLEMENT_REQUIRED` | 当前必需证据尚欠缺且允许补正；必须列出确切字段与所需证据组。 |
| `POLICY_UNKNOWN` | 校别、有效规范或条件真假不明；不能把未知当假而走宽松路径。 |
| `DATA_UNAVAILABLE` | 有权系统暂时不可访问或未获读权限；与“权威查无此人/此保单”严格区分。 |
| `DATA_CONFLICT` | 同一版本或同级有效证据关键事实相冲，无法由正式更正或上位权威消解。 |
| `AUTHORITY_MISSING` | 组织者、经办、审批角色缺有效授权；申请事实不等于审批许可。 |
| `AWAITING_APPROVAL` | 材料可送审或已部分签批，等待有权人员/机构作实质决定。 |
| `MANUAL_REQUIRED` | 风险、安全、法律、涉外或专业实质判断超出自动系统边界。 |
| `FORMALLY_REJECTED` | 有权机关对该活动/版本已作拒绝决定，有可追溯决定ID。 |
| `APPROVED_PENDING_ACTION` | 有正式许可记录但尚需对应版本的行前条件、备案或执行检查。 |
| `EXECUTION_RECORDED` | 实际执行事件已有权记录，不等于每名参加者获得学分或经费。 |
| `ROUTE_OTHER` | 事实证明为独立其他事项，返回路由而非错误驳回。 |
| `WITHDRAWN_OR_EXPIRED` | 原申请正式撤回、取消、废止或超过明确批准有效范围。 |
| `REVIEWED_AND_RELEASED` | 只能在有权学校系统真实签发行前许可且条件核验后展示其状态；模型自身不可生成。 |

## 11. 全生命周期：补件、重审、变更、撤回、执行与审计
| 阶段 | 必须完成的事实 | 允许产生的真实业务事件 | 缺失/不可达处理 |
|---|---|---|---|
| `ST-00` | 接入及政策定位 | 接收事项、确定学校/业务配置 | 政策不能定位→POLICY_UNKNOWN；保留申请不自动放行 |
| `ST-01` | 组织主体与入口资格 | 组织单位、代理与业务目的核对 | 未授权→AUTHORITY_MISSING；范围外→ROUTE_OTHER |
| `ST-02` | 计划及申报材料受理 | 申请表、行程、名单和风险初稿核对 | 缺件→SUPPLEMENT_REQUIRED；冲突→DATA_CONFLICT |
| `ST-03` | 安全实质材料预审 | 车辆、保险申请、预案、接待等条件核验 | 字段齐全也不自动生成安全同意 |
| `ST-04` | 有权部门审签 | 学院/主管部门/保卫或领导分级签批 | 未形成→AWAITING_APPROVAL；正式否决→FORMALLY_REJECTED |
| `ST-05` | 行前确认 | 清单冻结、保险、培训、签署和活动范围核对 | 仅有正式批准+当前行前条件齐全才可报告已具备行前条件；不得自己发许可证 |
| `ST-06` | 已批变更复审 | 新旧成员、路线、运输、时间的delta核对 | 旧批件仅对原批准快照；新版本须新审批 |
| `ST-07` | 执行与实时风险 | 日报/人员清点/事件上报、预警跟踪 | 高风险→人工应急，机器无继续实施决定权 |
| `ST-08` | 返校核销与安全归档 | 返校确认、例外事故记录、档案封存 | 经济报销与实践成果评估转相邻事项 |
| `ST-09` | 撤回/正式否决/过期 | 记录既有决定的不可覆写历史 | 旧批准不能被当前申报人重新激活 |
| `ST-10` | 复议/合法重新申报 | 新决定、新activity revision与历史关系 | 保留旧事件审计，不默认为否决已撤销 |
- **重审触发**：申报材料变动、人员名单变更、保单补录、天气/路线/交通风险变化、学校制度版本更新、签发人权限变动、系统数据由不可达恢复、同级官方来源更正、超出批准时段、撤回/已拒后合法重报。重审生成`review_run_id`，不覆盖前次结果。
- **版本冻结**：获批活动把人员/路线/运输/时段/保险核验范围与`approval_id`锁定；变更必有新`request_version`，对差异部分补证同时复核整体风险与审批层级。旧批准版若合法仍有效，不能让未经批准的新版本自动继承其许可。
- **取消与正式否决**：申请人撤回意思表示与有权部门正式撤销/拒绝事件独立；不能让学生点撤回就去修改已签发的批准原始事件；后续重报需新版本或新案并关联历史。
- **执行期突发事件**：实时重大风险应通知现场带队和保卫/应急有权人员，人工处置；不把模型当救援调度、气象预警系统或医师。事后报告是发生事件后的合法资料，而非初审的先决条件。
- **归档**：存每次规则运行的profile版本、查询结果及失败、证据hash、审批签发人、时间、权限角色、规则和改动摘要；个人敏感材料按校方保留制度和最小权限访问。
## 12. 合法例外、人工判断和权限边界
| 例外或冲突 | 审核器应支持的合法处理 | 不允许的捷径 |
|---|---|---|
| 学生合法更名、姓名误写与身份连续性 | 身份唯一键+学校正式更名/更正证明重新关联，不单看姓名字符相等 | 假定名字类似就是同一人或造假 |
| 学院为团队统一投保 | 使用正式保单名单或校方台账进行人员和区间核验 | 强制每名成员上传付款收据 |
| 指导教师与现场负责人不同 | 依该专项对两种角色分别做在职、授权和陪同条件核查 | 把指导签字替代现场带队与主管批准 |
| 学校允许电子审批 | 有权OA签发证明可合法替代纸签，保留来源哈希 | 对所有学校套CDUT2025本人亲笔条款 |
| 家长知情不适用 | 仅当`BR-10`所加载项目确有要求且本人落在适用人群时触发 | 对所有成年人、教师强行要家长同意 |
| 已知名单个别成员退出 | 生成正式变更、保险撤保/调整、交通人数变化等单项复审 | 审核器静默删人后批准其它人 |
| 商业包车改公共交通 | 依据新版交通方式重算需证据并正式变更 | 忽略原合同变更及路线安全信息 |
| 教学实习有教学部门批准 | 安全职责如学校另有规定则并行处理；教学与财务只作关联引用 | 出差审批表即视为安全许可 |
| 特殊高风险野外考察 | 校内风险及有权专项许可多流程核查，模型只做材料与事实提示 | 资料齐全即签发专项许可 |
| 事故/医疗敏感数据 | 授权安全角色处理，普通管理者仅可见风险结果和必要操作 | 在评审报告中复制全员健康或监护人电话 |

**人工必须决定**：是否批准活动组织与高风险停启、保卫安全专业评估、组织领导审批、特殊涉外与专业野外许可、争议证件真实性、紧急救援处置。真实行政决策不得由`PASS_FORMAL`替代。
## 13. 学校profile、配置优先级与已知缺口
### 13.1 Profile最小键及加载次序

`policy_profile={school_id,authority_doc_id,version,effective_from,to,activity_type,organizer_type,student_or_staff_scope,project_batch,applicability_threshold,headcount_method,min_lead_days,calendar_id,required_documents_by_stage,signature_modes,authorization_roles,approval_chain_by_scale_geo,insurance_scope,exception_authority,source_ids}`。

校本与项目条款在其生效条件下使用，法律/上级正式规定优于当期项目通知，之后才是校内正式规则；同一学校部门的特别项目规则仅对该项目生效；外校规则仅用作样例或在该校自身profile中使用。冲突且无法确认正式效力→`POLICY_UNKNOWN`，不得选最严数字或最宽松数字。

### 13.2 可确认的四组研究profile
