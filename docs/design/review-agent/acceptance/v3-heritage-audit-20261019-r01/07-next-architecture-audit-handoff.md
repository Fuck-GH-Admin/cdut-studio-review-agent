## 一、第二轮应严格核对的架构冲突
1. **唯一案卷/事实写权**：从 V1 `case-store.ts` / `ReviewCase` 到 V2 `case-store-v2.ts` / `CaseAggregateV2` / D4 `createD4ClientCase`，查究竟哪些 Renderer/IPC/主进程入口依然绕开统一命令事务；给出双向迁移及修订不丢的行为图。
2. **唯一运行/Check/覆盖权**：D2 不可变 Plan、D3 gate、V2 `RunV2` / `coverage-ledger` / Pi `submitPiReviewResultV2` 的真实调用链。不得将合成 28/30 pending-only 或 PR CI 算业务真值。
3. **两个 batch 并不等价**：D4 `review-d4-case-batch.ts` 是导入材料，P06 `batch-store.ts` 是审核调度与处置；用对象生命周期证明合并哪些 DTO、保留哪些独立事务。
4. **跨两支 source/IPC**：D4 W1 和 P06 R03 都有独立 `review-ipc.ts` 变更，且 main/D4/P06 tree blob 不同。建议三方同名文件函数级 diff，列出各自独有能力和冲突风险。
5. **SourceRef/Office/Owner/Pi 栅栏**：验证预览路径只读、原件 hash、版本、视图隔离、五工具 Main 授权、撤权/等待后重验和 Run provenance。并记录上游 #71 阻断状态。
6. **领域完整性**：#89–#96 与 #97 的原文母版/责任/Check/source/manifest 比对，标出仅合成编译通过与真实学校业务确认的距离。
7. **历史保留策略**：区分真正可直接复用的无状态算法/事务边界与实现繁杂的双引擎补丁；不要用 LOC 和 PR 数决定。
8. **只读调查阻断补完**：若有本机完整 Git，执行第一轮缺失的按 SHA `merge-base/cherry/patch-id` 并出具可核结果；不要重写第一轮固定快照。
