## 0. 一句话目标与阶段责任

**D3 的成功不等于做出 B01/B02 两个模块，而是交出让五个独立业务会话能够实际制作、测试、导出、复用和维护完整审核模板的可靠工具。**

D3 交付“能力和公共契约”；D4 制作“具体业务模板并进行反向压力测试”；D5 才是“人类编辑体验与界面优化”。**D4 验收发现 D3 的表达/编译/模块库缺陷，要返工 D3，再用固定新基线重做受影响的 D4 制作和测试；五套模板统一验收合格之前不进入 D5。**

本阶段设计源于用户的五个独立 G01 业务研究会话，它们已有完整 Markdown 业务规范：
- 学籍身份信息更正（I）
- 档案利用申请（A）
- 特殊校园卡资格（C）
- 专项证明与用印（S）
- 政审材料程序审核（P）

这些原始 Markdown 不一定存在于 Git 仓库。**D3 不应从第 16 号的概要中“恢复”原业务条文，D4 原业务会话须提供对应原文及来源核验状态。**

## 1. 本轮不变的架构决定

1. **Agent-first 而不是 Blender-like 程序图。** 模块定义审核责任的“目标—适用—依据—必核事项—完成标准—限制”，不规定 Pi 阅读/工具调用顺序。模块可由自然语言、可选受控规则、嵌套模块、专业执行器混合实现；不强制 Claim/Evidence/AST/图坐标。
2. **一个统一模板目录，按独立审核目的建完整模板。** 同一模板内支持多个分支、主体、对象与逐操作责任；不得每有分支就另建模板，也不得合并不同审核目的。
3. **制作平面与审核运行平面分离。** 制作 Agent 编辑模块与模板；运行 Agent 使用已经固定的审核任务及现有 `RuleSpec / Pi` 服务，不在审核运行时自由改写模板模块图或启动第二套审核 Agent。
4. **公共复用不是默认正确。** 共享的是确有同一局部语义的责任；跨校、跨业务不自动继承资格条件、证据法律效力或行政批准权限。模板专属模块、完全不引用共享模块的完整模板均合法。
5. **制度适用与内容核验是两回事。** `source.kind`、内容核验、适用性以及是否有权正式发布需独立处理；未核校规/外校参考/测试模拟不能变成本校强制拒件条件；正式审批/组织鉴定继续有人类权限门控。
6. **失败要可发现。** 无法编译的高级约束、未知分支、悬空对象、坏来源、循环引用、版本错配，必须返回可定位问题；禁止静默删除检查义务、缩小审核范围、伪造“已通过”。
7. **旧结果不可漂移。** 已固定模块版本、发布模板及案卷运行快照不受后续改动影响；新版本由有权者显式迁移并重验。

## 3. 共享模块的最小资产契约（语义为主，不先锁死最终 Schema）

下表是**功能必须满足的契约**，不是要求立刻创造一套新的复杂 DSL。D3 开发者应先对比 D1 现有类型，尽量做增量扩展。

| 概念 | 必须具备的语义 | 验证方法 |
| --- | --- | --- |
| 模块定义 | 稳定 ID、**发布/冻结版本及内容摘要**、名称目的、适用与排除、局部检查责任、完成标准、禁止事项 | 独立读取/导出/再导入后含义一致 |
| 模块所在范围 | `workspace-local`（可随草稿 revision 修改）与 `shared-frozen`（不能同版本原地修改）明确分开 | 试图覆盖冻结资产被拒；草稿可以有历史修订 |
| 依赖引用 | 记录固定 `moduleId + version + digest`（或等价不可变锁），实例路径、业务条件、对象范围及有限参数 | 不存在版本、摘要错、循环依赖、悬空引用被拒 |
| 来源与制度等级 | 模块中的“制作来源”及**每个实际检查在模板实例下**的适用依据；用户请求、合成、跨校参考、待核政策不得混同 | 同一模块在不同模板有不同依据，不能跨模板偷渡权威 |
| 显式覆写 | 新增、受控参数化、经授权指定目标的替换；变更理由及受影响清单 | 不支持“最后一个覆盖前一个”“自动更严格” |
| 生效产物 | 展开后的必核责任清单、条件/对象、规则来源、技术/行政边界、固定指纹和可定位错误 | 预览与真实 Pi 任务包对照，不能仅比文本相似度 |
| 反向引用索引 | 某个冻结版本被哪些工作区/模板/测试使用；升级受影响的版本清单 | 模块变更不改变旧引用，能输出差异与回归建议 |
| 验证资产 | 正例、反例、边界例、未核政策、材料版本变化、越权替代；测试输入/金标分离 | CI 与独立验收均可复跑，报告对应确切代码和锁文件摘要 |

示意引用（**只表达应有的语义，不是已实现 JSON Schema**）：

```yaml
moduleUse:
  moduleId: review.delegation-scope
  version: 1
  digest: "<sha256-of-frozen-definition>"
  instanceId: archive-application-proxy
  appliesTo: current-case/archive-item-operation
  parameters:
    matter: archive-access
  policyBinding: archive-local-authority-source
```

**身份不能混淆**：`workspaceId + revision` 是制作草稿历史；`moduleId + version + digest` 是可供多个工作区放心引用的冻结内容；`TemplateVersion.version` 是完整模板版本；`ReviewRunV2.inputManifest` 与 D2 固定任务包是运行证据。四者不可互相代替。

### 3.1 变更行为及版本规则

- **草稿保存**可以修改工作区里的某个 `moduleId@version`，但应追加工作区 revision。
- **共享冻结**需要明确动作，依赖完整性验证、冲突检查和至少一个可复跑用例。**冻结后拒绝同 ID+版本但 digest 不同的写入**；修订必须产生新版本。
- **模块被引用**时锁定不可变内容；当前工作区的另一个同名草稿不得悄悄盖住冻结版本。
- **显式升级**提供旧/新版本、生效检查及来源差异、受影响模板列表、需要重新跑的案例；原引用保持旧版直到确认升级。
- **回滚**只针对草稿/新编译产物选回旧版本，**不删除**已被使用的冻结资产或覆盖已产生的历史运行结果。
- 如果人工改变了业务依据或取消旧政策有效性，不允许在旧快照中直接改文字，应通过明确失效/新版本/相关案例重审实现。

## 4. 面向制作 Agent 的最小可操作工作流

D3 必须交付一个**真实可运行而不是示意的命令/API 入口**，能完成下面的闭环。具体 CLI 子命令/函数签名待实现后以实际源码为准，本节不给尚未存在的命令假名称：

```text
读取一份完整业务 MD（带来源定位）
      ↓
查询并选择现有冻结模块（可拒绝不适用的模块）
      ↓
建立本地作者态草稿（允许原创局部语义模块和业务专属要求）
      ↓
引用冻结模块 + 配置合法参数、情景/对象 + 绑定来源
      ↓
增量验证 → 生效预览 → 形成候选技术审核任务
      ↓
同一套输入的正例/反例/未知/越权测试
      ↓
导出可携带交付包（再导入复验）+ 差异/未实现问题清单
```

D3 工具应提供以下**最小行为**：

1. `discover / inspect`：按目的和能力查找模块，可查看版本、接口、限制、来源要求、使用案例、依赖与冻结状态。
2. `draft / reuse / edit`：在工作区创建完整模板或局部模块，引用固定共享版本，给定 expectedRevision 原子提交一组修改；错误不造成半成品。
3. `validate`：至少检查引用、参数、依赖环、来源适用性、不可表达条件及违规行政输出，返回**具体责任路径/模块实例**。
4. `preview / compile`：给定业务场景与作用对象，生成有效任务、来源、覆盖责任、预览指纹；必须显示“不适用/待确认/技术异常/编译不支持”的原因，不让 Agent 自行脑补。
5. `test / diff / export / import`：基于冻结测试包复跑，出具可机读结果；比较工作区和模块升级前后；携带模块锁、作者态、来源映射、有效任务快照与验证清单离线导出再导入。
6. `report-gap`：无法忠实表达原业务规定时产生结构化缺口，指向原 MD 的位置、必要语义、受阻操作与建议归属，不用文本警告代替有问题的成功码。

**Agent-first 的工程验收方式**不是测使用者能否在画布里手工拼节点，而是实际用这些受控工具完成两次不同业务的编辑、升级、错误恢复、重读和导出，操作能自洽、不会反复出现“需要猜 ID/补一个隐藏字段才能继续”。可以记录失败命令和重试次数，但不设未经基线实验验证的武断调用次数阈值。

### 4.1 D4 可以直接复制的最小工作示例必须随 D3 提供

交付一套**可执行的**合成示例（至少两个）：
- 一份普通文本审核：零复杂对象、一条独立语义责任，确认没有 Claim 图时仍能跑。
- 一份复杂 G01 片段：C 的双分支或 A 的逐操作，使用真实 D2 案卷与 Pi 回执接口，能够看到未确认/失败/完整技术预审的区分。

样例必须注明是合成规则/模拟模型回执、所需运行环境及真实 CLI 命令。**不要给 D4 五个会话一份过期的 CLI 伪代码**；D3 开发完成时需要更新此文档或专用操作说明，附实际执行命令、fixtures、输出定位、验证日志与版本。

## 5. 首批候选模块：B01/B02 不是全部 D3 交付

| 候选 | D3 试验目的 | 严格限制 | 遇到不适合复用时 |
| --- | --- | --- | --- |
| **B01 有权代办与授权范围核验** | 在 A、C、S 中寻找可稳定共用的“代理人与对象/事项/期间是否被授权”局部责任 | 委托成立不等于馆藏开放、校园卡资格或用印审批；本校制度效力由业务方确认 | 将委托范围核对缩为更小的共同责任，业务资格继续模板专属 |
| **B02 待证事实与证据链覆盖核验** | 在 I、C、A 中复用事实与材料关系核验的工作说明/可选工具 | 一证多用不能变成一证自动批准多事项；合法替代范围取决于本案适用制度 | 保留读取/证据定位共享能力，特殊证成标准留在完整模板 |

要求至少在**两个确有共同局部语义的业务情景**中试验一个共享候选，并留下不适用/拒绝复用的对照记录。D3 的“复用”不得变成硬性 KPI：**不强迫五份模板都采用 B01/B02**；它们可以是候选、局部模块，或者试验后决定撤销。

**不要求 D3 在五套完整业务都制作完成前先证明业务等价。** D3 只交付可复用的机制与受控小样本；真正的五模板全量等价验收由 D4 完成，发现反例再回修 D3。

## 6. D3 → D4 的正式交付包（必须可由另一个独立会话接手）

建议为每次 D3 可交付构建生成一个固定 `D3 Release Bundle`（命名待工程实现），**不要求提前做可视化 UI**。它至少包含：

| 文件/信息 | 用途 | 必须能验证 |
| --- | --- | --- |
| ① 固定代码 commit / 测试环境 | 五个 D4 会话使用同一版工具 | SHA、依赖安装/运行条件、适用 D2 版本 |
| ② 共享模块索引与内容快照 | 供 Agent 查询/引用，含本地模块与冻结模块区别 | ID+version+digest、用途、限制、依赖、来源/适用说明 |
| ③ 真实可执行制作说明 | 新会话不知道仓库内情也能成功制作样例 | 命令或 API、输入/输出示例、错误恢复 |
| ④ 作者态工作区与模板交付规范 | 五个会话用同一输出口径 | 格式版本、来源绑定、实例 ID、分支/对象表达、未映射项 |
| ⑤ 运行/候选映射及可观测账本 | 验证 Pi 真正收到审核责任 | Check/Rule/Source 映射、任务包摘要、材料版本与回执 |
| ⑥ 测试驱动与基准样例 | 会话可在独立配置目录复跑 | 测试命令、正反/未知/替代场景、报告位置 |
| ⑦ 已知限制和缺口上报格式 | 遇到当前系统不支持可立即反馈 | 错误码、可复现数据、归因、允许降级与禁止降级 |
| ⑧ 交付版本清单 | D4 汇总验收与返工的唯一基准 | 工具提交 SHA、模块锁、案例/金标版本、输出摘要 |

**技术试验 vs 正式使用**：候选 `candidate-held`、D2 技术案卷和模拟制度不能绕过正式模板发布权。D3 可提供完整的**技术预审**制作包；未授权的校本业务依旧只能以待核规则/模拟运行验收。D4 不得声称校方发布成功。

## 7. D3 自验收门槛：先交给两个“陌生 Agent”，再交给五个业务会话

| ID | D3 验收实验 | 通过条件 |
| --- | --- | --- |
| D3-01 | 首次使用新配置目录，从零创建文本审核模板 | 自然语言责任可在不建复杂关系模型下验证/预览/执行 |
| D3-02 | 新会话从共享库查找、引用模块，另一个工作区引用同一冻结版 | 不需复制模块源文件；两次生成相同局部语义与 digest |
| D3-03 | 冻结资产尝试同 ID+version 覆盖；缺依赖、循环、坏版本/摘要 | 拒止并保留旧快照，明确错误路径 |
| D3-04 | 一个模板对公共模块参数化，另一个模板有不同的制度适用性 | 两边来源独立，不把外校规则升级为本校强制标准 |
| D3-05 | 模块升级、旧模板不迁移，新模板显式升级 | 旧任务包和历史运行不变化，新版差异/影响可见 |
| D3-06 | C 双分支及 A 查阅/复制分别编译并形成 Pi 真实回执 | 与 D2 作用范围与来源保护一致，未经确认的规则仅待核 |
| D3-07 | 同一模板含无法表达的替代证据/阶段条件 | 明确 fail-closed + 能导出缺口，不假称已经完整映射 |
| D3-08 | 源规则含恶意命令/假权威文本 | 不作为 Agent 系统指令，不获得发布/操作权限 |
| D3-09 | 导出 → 全新配置目录导入 → 预览/编译/回归 | 同一锁定定义得到等价任务包；差异可解释且可追溯 |
| D3-10 | 两个不熟悉内部代码的制作 Agent 仅按交付包操作 | 独立完成最小模板和一个复杂样例，错误可自诊断/恢复，不需要维护者暗中手工改状态 |
| D3-11 | 全仓 CI + D0.5/D1/D2/D3 专项回归 | 对同一提交的绿灯才有效；记录跳过项目，不用单测绿灯覆盖整仓失败 |
| D3-12 | 失败时输出包含受影响源规则/模板/实例/运行的对应关系 | D4 可提交可复现问题，不要求原作者猜测问题发生在哪层 |

**D3 可以进入 D4 的条件**：D3-01 至 D3-12 **全部有实际执行记录和可核验结论**，其中任何失败或未运行都不能被标为通过；仅允许**明确记录、且被统一验收者确认不妨碍五套模板制作或正确性的非阻断限制**。若 D3-10 需要大量隐含知识才成功，说明“Agent-first”还没有真正达到交接标准，应先修 D3 再启动五路业务制作。

无需完整 UI、真实校方认证、全部五套校规核实、正式批准流程或百分之百真实模型准确率即可作为 D3 的**技术交付**；这些不可被伪称已完成。

## 8. 测试质量、回归与报告格式

- **结构正确**：来源、身份、条件、对象、模块锁、指纹、回执校验。
- **业务语义保持**：正例、反例、合理替代、未确认制度、跨操作/主体防串用，不新增无依据必交项。
- **实际维护收益**：选一项公共模块的语义修订，比较复用与复制粘贴的受影响修改位置与测试量；记录失败的复用试验。
- **真实模型单列**：结构化合成回执只能证明接口正确；在线 Pi 模型的阅读、遗漏、合理解释与出处准确性需独立标注，不应拿“模型自己说通过”当金标。
- **运行隔离**：所有测试使用独立 `PROFER_CONFIG_DIR`、合成材料及冻结金标；测试不写生产配置目录、不接真实学校数据。
- **安全**：原文件是数据；内部工具执行权限、外部来源可信度及权限提升严格分离。对于新的模块注册/导入路径，还要检查不可信 ID、文件名和归档路径不会造成跨目录读写。

每次验收报告至少包括：代码 SHA、D2 基线、共享库版本/摘要、复现实验、通过/失败/未执行、真实运行命令、输出位置、金标来源、已知限制、后续缺陷列表及 D4 准入结论。

## 9. D3 阶段结束后如何交给 D4

1. 冻结一个 D3 交付版（**不等于正式校方模板发布**），锁定代码、模块及示例测试包。
2. 按 [24 号契约](24-d4-five-template-authoring-and-feedback-loop.md) 为五个业务会话分别交付统一制作说明、相同工具版本和独立工作区。
3. 每个会话先比对自己的**原始完整 Markdown**，再编写/组合完整模板；不能让模块库压缩或改写业务目标。
4. 五个会话提交后统一验证；**不合格先归因**，只有共性能力/模块库/编译器/Agent 编辑接口缺陷回到 D3，业务规则和样本标注问题回到 D4 会话。
5. D3 修复产生新代码或共享模块版本；重新发布交付包，受影响 D4 会话**显式迁移并重跑**。如此循环直到五份模板整体达到 D4 的技术与业务质量验收，之后才进入 D5。

**本文件不规定 D5 的界面实现。** D5 应依据五次真实 Agent 制作过程的操作数据、重复失败和修改成本来决定人类编辑器要简化什么，避免提前做巨大拖拽画布。

## 10. 进入 D3 开工前需确认的依赖

- 五份原始业务 Markdown 归属各业务会话；制作 D4 前需要能直接读取其全文、引用来源与离线测试材料。

- 如果 D3 技术实现发现此文档某条验收超出当前阶段可实现范围，应提交带反例的书面变更，由统一验收者裁定；**不得未经批准把 D4 要求压缩成示意演示或把不支持情况伪装为通过**。
