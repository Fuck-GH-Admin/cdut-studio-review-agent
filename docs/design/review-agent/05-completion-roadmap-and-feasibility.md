## 1. 本轮结论

**可以在 CDUT-Studio 现有基座上完成本地通用审核 Agent。** 不需要另建 Chat、审核专用模型设置、独立服务端或本地数据库。主要工作是补齐业务应用层、可靠执行和用户操作闭环，同时修正已有 V2 基础中不完整的契约与算法。

“老师暂时提供不了接口”只影响真实身份、校方资料核验与结果回写，不影响本地模板、真实材料审核、人工决定、补件、复审、批次和评委评分。先完成相同业务合同的本地实现，未来由适配器替换数据来源和流程所有者。

完整目标仍是 [02 产品设计](02-product-and-templates.md) 和 [04 验收契约](04-acceptance-and-evaluation.md)；本组 05–07 补充当前代码差距、操作设计和实施决策。后续交付不能以“有类型、有纯函数、有单元测试”代替用户流程通过。

## 2. 当前到底完成了什么

其中失败冒充模拟成功、证明漏入上下文、多依据显示、过期结果、窄屏定位、PDF worker 等已有修复，不能继续当成全部尚未处理。受控模型服务验证了通信与操作行为，**没有证明真实模型的审核准确率**；Linux 开发构建也没有证明 Windows 安装包开箱可用。

### 2.1 需要纠正的“基础已完成”误判

以下依据实际函数体核对，注释不能作为验收证据：

1. `run-service-v2.ts` 当前在运行开始与结束保存；`onEvent` 在整图执行结束后转发，尚非逐节点落盘或实时进度。`checks/opinions/coverage` 也没有装配真实产物。
2. `review-run-graph.ts` 按业务阶段线性映射节点；一个 `auto-check` 仅变为 `parse`，不会自动展开完整解析—提取—绑定—检查管线。无可执行节点仍可能返回 `completed`，恢复也没有核验产物。
3. 输入 hash 未包含 `caseFields`、真实政策内容及解析修订；启动传入的 observations/evidence 快照为空，政策版本被写死为 1。不能据此声称旧结果不会混版。
4. `deterministic-engine.ts` 尚未实现所有已声明的 select/aggregate 分支；缺失去重键可能被拼成同一空键，空集合择高、精度与计算输入引用仍需补齐。
5. `coverage-ledger.ts` 未真正展开分组计划，也未把 `registered` 和不符合结果纳入“全部符合”的阻断条件。零计划不能自然证明全部符合。
6. `business-workflow.ts` 把初审通过直接设为 `decided`，把驳回与退回都设为待补件；部分补件/申诉操作不统一增加 revision，也没有统一持久化与请求去重。
7. 评分提交尚未完整验证 assignment、版本、重复维度、有限数；汇总可能将缺维度/N/A 隐含为零贡献，排名的其他策略没有完成。报告取“最后决定”会混淆事项、初审和终审。
8. 六模板引用的政策没有对应的完整政策仓库。草案不等于六套可直接使用的业务。
9. V1→V2 迁移 hash 来自文本块，不是原件字节；非图片 assetPath 可能为空，事项引用也需要映射为真实 documentVersionId。旧版扁平文本不能补造真实页码。

这些问题有明确修复路径，不能只为现有函数加按钮后交付。

## 3. 最终用户得到什么

### 3.1 普通使用

- 选择模板，填少量基本信息，上传材料，一次点击“开始审核”。
- Agent 自动分类、解析、提取、绑定证明、执行规则、计算和生成解释；歧义集中为待办。
- 用户能核对原件，改识别错误、补材料、处理误报；系统保留原值、出处和更正历史。
- 老师按阶段决定，学生收到可操作的反馈；补件、复审、申诉都有终点。
- 组织者处理批次，评委独立评分，规则正确汇总并定稿；失败案不阻塞其他案。
- 负责人从空白配置新业务，不需要修改源码、写 Prompt 或新增专用页面。

### 3.2 没有学校接口时

用户可在单机中切换工作视图演示流程；真正离线分工使用独立工作副本和学生补件包、评委评分包往返。界面和报告标明身份来源为本地、模拟或校方。

本地产品负责自己的待办、版本和结果；模板不得强制要求不存在的校方成绩查询。外部真伪无法核验时生成明确的“需人工/外部核验”任务，不能把材料上的声明当作已经查证的事实。

## 4. 可行性与必须验证的边界

| 方向 | 判断 | 采用的设计 | 必须补的证据 |
| --- | --- | --- | --- |
| 单案业务闭环 | 高可行 | 现有 V2 类型与纯函数 → 应用命令 → JSON 聚合存储 → 三栏操作 | 从识别错误到补件终审的真实 UI 全程 |
| 无代码模板 | 高可行 | 有限字段/条件/计算/阶段 DSL，表单向导；AI 只起草 | 六模板完整样例；第七业务从空白配置通过 A15 |
| 可靠计算 | 高可行，现有实现需修正 | 有限计算算子、十进制策略、程序重放与完整明细 | D04–D07、未知/零值/空组/同分边界 |
| 本地批量与评委 | 高可行 | 按案排队，独立评分记录与离线包，模板锁版本 | 100 案/500 文件、最低人数、缺评/N/A/名额验收 |
| Pi 自动审核 | 可行，需公共适配层小幅扩展 | 复用 Pi adapter，新增审核工具配置与 executors | 工具只在本案范围运行；中止/恢复；实际模型调用记录 |
| OCR 与原件定位 | 可行，识别质量和包体需实测 | PDF 分页 + OCR 端口 + 位置索引；复用预览 | 中文证书/模糊图/扫描页；离线资源和目标机验证 |
| 语义正确率 | 不能由结构设计保证 | 结构化输出、引用核验、真值集和人工确认 | 04 §5 固定集与真实模型评测；不能报虚构准确率 |
| 学校接入 | 核心可准备；真实上线取决于校方 | Repository/SchoolPort/身份端口与能力协商 | C 类先过；有真实接口后执行 S 类 |
| 开箱安装 | 可设计，当前未证明 | 解析/OCR/worker/运行资源随包，自检与明确状态 | 无开发环境的目标机安装、断网示例与真实材料 |

手工录入和明确失败是降级能力，能保持业务继续处理；它们不能替代最终要求的 OCR、自动分批和支持格式验收。对不可读材料，只有有权用户作出明确且带理由的处理，才可改变对应业务要求；不能自动把它移出分母。

## 7. 发布时如何判断完整

- 每个模板都覆盖正确、缺件、识别错误、违规、失败与人工处理路径；六模板不是六个名称。
- 用户从新案到明确结束状态，无需终端、配置文件或开发者修数据；后台服务基础不能替代操作入口。
- 一案所有有效材料、适用检查、未知范围与来源均可查；零问题只有在账本满足时才能显示完整符合。
- 本地全部 A/C、固定集、易用性和目标机安装有证据；真实联网 S 保持独立状态。
- 无商业化运维或计费要求，但版本、决定、恢复、计分和可见范围要正确；这些直接决定功能是否可用。

执行人员读 05 排顺序、读 06 定交互、读 07 改代码；验收人员以 04 为总门槛，并用 07 的增补回归验证已有基础修正。
