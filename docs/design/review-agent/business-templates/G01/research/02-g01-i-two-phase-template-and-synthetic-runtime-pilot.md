# D4｜首套真实 G01 模板：制作 → 合成数据运行的两阶段试点协议

> **状态：PLAN / NOT-STARTED（2026-10-17）**。本文件是由 [V1–V3 离线研究](01-offline-v1-v3-independent-agent-study.md) 推导出的下一步实验规范，**不意味着本轮已制作 I 模板、提交了 D4 业务 PR、建立 Pi 案卷或完成 Gold**。只授权按既有 D3-R0 技术契约设计与实施；实际开始由用户另行下达任务。

## 一、我们实际要做的两件事

**第一件：制作技术模板。** 从完整、真实的 G01 业务设计 Markdown 逐条理解审核责任、办理分支和例外，生成可追溯、可修改、可编译、可导出/重新导入的 **D1 作者态 + D3 模块组合 + D2 技术计划**；不止写新 Markdown 或一个固定案卷的 JSON。

**第二件：用合成案卷运行和审查。** 创建虚构申请人、虚构证件/证明、版本差异、缺件/未知/合法替代/越权/阶段组合，生成与当前申请精确对应的 Check/Subject/SourceRef，实际运行 D2/Pi **技术服务**与独立 Gold 对照。合成回执≠在线模型业务准确率，技术可转交≠学校正式批准。

**两阶段可以循环反馈**：第二阶段发现「有规则但无法按输入表达」「设计正确但代码字段误读」等问题，退回第一阶段定向修模板；若现有公共引擎真正不支持，则报告最小 `tooling-blocked`，交公共分支讨论 D3-R1，不允许在 I 业务分支暗改共享内核。

## 二、为什么建议先选 G01-I，而不是马上五路并行

首件建议：**I｜学籍身份信息更正审核 v1.7**。

- 原件：`docs/design/review-agent/business-templates/G01/originals/g01_student_identity_complete_template_v1.7.md`，源字节 SHA-256：`52ae0cdc27a16bb46659cd43d3e78632c44d8b5ccc86a18559b263512f51f329`，原始 61,389 字节，约 535 行。
- 内容：**1 套模板**、13 类业务条件情形、28 条已编号审核规则、28 项字段词典；正文的例外、阶段、对象、权威来源也应独立入账。不要将 13 个分支或 28 个字段误认为要分别产生独立模板。
- 技术价值：姓名/证号/出生日期更正、双字段同源证据、旧证与新身份连续性、证据替代、毕业前后分流、2024 研究生校规待核、留学生可能的并行管理链和禁止代替学校审批都能形成较好的对照。
- **避免先验偏差**：档案 A 此前有专用 `instantiateD3ArchiveCaseV1` 及旧试验 A/B，先试 I 能验证更通用的 D3 作者路径，而不是把档案专用 schema 误当全 G01 共性。档案 A 保留为第二个跨操作压力对照。

### 固定两个来源，不要混淆版本

- **技术源码**：已签 D3-R0 固定提交 `4b191c729f3d5f8135c73b87c17642023f6c3986`，冻结发现分支 `release/d3-r0-20261011`；[37 号技术交接手册](https://github.com/Fuck-GH-Admin/cdut-studio-review-agent/blob/4b191c729f3d5f8135c73b87c17642023f6c3986/docs/design/review-agent/37-d3-r0-frozen-release-and-d4-handoff.md)。
- **业务原件**：本仓库 `main` 的 G01 原文存档（本次审阅时为 `8989941b6fb5651564e32d11c4215b6a6d5a5209`），[source-manifest.json](../source-manifest.json)。I 的来源哈希同时写在 D3-R0 的 [机器锁表](https://github.com/Fuck-GH-Admin/cdut-studio-review-agent/blob/4b191c729f3d5f8135c73b87c17642023f6c3986/docs/design/review-agent/fixtures/d3-r0-handoff-manifest.json)。

**关键组织方式**：技术开发从 D3-R0 **固定 SHA 派生试点分支/工作树**；从已固定 main 读取 I 业务原始文件作为**只读材料输入**（Git show、旁路路径或经校验的原件包），不整体合并 main，不让工具底座漂移，也不把后续作者提交 SHA 误称 D3-R0。首次在完全未改的 D3-R0 检出点执行 `review-d3-r0-verify.cjs --expect-sha ...`；进入后续 D4 作者提交后，用提交祖先关系、模块 digest 与单业务文件 SHA 检查，不对已产生新提交的作者分支强求 `HEAD == D3-R0`。

## 三、两阶段的工作拆分和交付

### 阶段 1：完整原文 → D1/D3 模块化技术模板（模板制作 Agent）

**输入**：完整 I 原文 + SHA、D3-R0/第 24、32、37 号契约与实际 CLI、经确认的仓库修改范围；**不看独立 Gold 和第二阶段隐藏案例**。

执行顺序：

1. 验证原文 SHA，建立 `source-catalog`：28 条有编号的审核规则 + 13 业务条件情形 + 正文材料槽/事实词典/例外/阶段/权限/来源等级；非编号责任须有真实原文锚点，所有内容为「一套业务模板中的分支」，不得为凑模块数拆模板。
2. 建立 `conversion-ledger`：每条原文责任明确指向模块/Check/Subject/SourceRef/RuleSpec/实例化条件，或标记 `manual-only`、`policy-awaiting-confirmation`、`source-missing`、`tooling-blocked`（带可复现输入、运行错误）；**禁止无理由消失或把待核校规变成本校强制材料**。
3. 读取实际输入结构，先确认每种证据的字段名、数据类型、枚举、单值/数组、对象和更正字段集合的关系。用有效原件示例建立**至少一份真正的正向 happy-path**，不以自己想象的字段生成全部自测。
4. 在既有 `ReviewAuthoringWorkspaceV1` 中制作按责任目的划分的本地模块，按真实语义决定是否复用 B01/B02；同一附件可覆盖多个更正事实，但不能自动扩展为核实本人身份、适用其他主体或正式批准。
5. 实测 D1 `validate/save/read/diff`、D3 `validate/discover/inspect/freeze/reuse/export/import`、D2 `preview` 等存在的 CLI；真实生成不同申请条件下的 **动态实例** 与 Check，而不是固定一个学生、一个字段的演示。档案专用 adapter 不得强行复用到 I。
6. 从干净环境重新导入携包，检查不可变模板版本、module digest、source hash、Rule/Check/SourceRef/Subject 与对应 plan fingerprint；保留真实命令、退出码、输出。无法表达的责任须有缺口票，不能降级为只用自然语言口头提醒。

**阶段 1 必交**（按第 24、37 号现有协议映射至真实工程目录，不发明运行时格式）：`source-catalog`、`conversion-ledger`、`workspace` 与 revision、共享/局部模块锁、至少两种不同申请实例下的实际 D2 plan、技术命令日志、export/import 证据、`tooling-blocked` 票、独立业务 Draft PR。

**阶段 1 最低关卡**：全文的关键责任均有实际去向；至少一个真实非空 Check/Source/Subject 链实际编译成功、另一个业务分支产生不同作用域；报源缺口不阻塞其余安全部分，但不得将「已生成 Check」等同「复杂条件已被程序门禁正确执行」。

### 阶段 2：合成申请材料 → 实际技术审核运行（独立 Gold + 运行验收 Agent）

**输入**：阶段 1 冻结的模板产物和 SHA、同一原始 I MD、**先于查看模板结果建立和冻结的独立 Gold**、合成申请材料。Gold 与审核 Agent 待审输入物理隔离；不能由模板作者查看自己的失败后倒改 Gold。

**建议首批 16 个合成案例（建议矩阵，执行前冻结精确定义与版本）**：

| 编号 | 场景/最小差异 | 必须被观察到的性质 |
|---|---|---|
| I01 | 在校本科生，合法更名材料完整 | 审核事实可转人工审理；不得输出校方已批准 |
| I02 | 姓名+证号同时更正，一份法定文书同时覆盖两事实 | 合法同源复用，不重复索取同一份材料 |
| I03 | 旧号→新号连续性证明齐全 | 身份连续性适用当前主体，不串别的学生 |
| I04 | I03 仅把证据主体换成另一人 | 应拒用此证据，不是本案事实待核 |
| I05 | I03 仅把已交证明的 verified 变为 unknown | 待核验与缺件分离 |
| I06 | I03 移除所有可用旧→新连续性证据 | 明确缺件而非自动通过或空泛人工核 |
| I07 | 多次申请使用相同附件证据，只在其合法覆盖范围共享 | 跨字段可复用，跨申请主体/无关联对象不可复用 |
| I08 | 研究生且 2024 现行校本更正规程未核 | 保留 `policy-awaiting-confirmation`，不造表格与审批链 |
| I09 | 来华研究生同时落入两类管理身份 | 不自动取两套部门要求并集或私自只择其一 |
| I10 | 已毕业，毕业当年原注册事实有错 | 按原文路由到历史学历注册勘误；不一律拒止 |
| I11 | 已毕业，毕业后新发生个人更名 | 不将新名字自动覆盖毕业历史注册；需路由/确认 |
| I12 | 只需修改学信网账号联系方式或账号显示名 | 正确分流账号服务，不能激活学籍更正审批 |
| I13 | 只有字符乱码/显示异常、源记录未变 | 数据显示修复分流，不等同法定更名 |
| I14 | 尚未到期的后续部门证明或签章阶段材料 | 不被错误归为申请人缺件 |
| I15 | 材料/模块/制度版本改变后重跑原案卷 | 旧结果不能未经确认直接复用；版本/来源可追溯 |
| I16 | 同时存在申请人缺件、材料待核、审批待办 | 报告全部问题，主状态不能掩盖其他责任 |

本矩阵不是现行校规材料清单；**具体「是否要求该材料」「何时到期」须由 I 原文确实支持，无法确认时写入 Gold 的待核状态，不得重演 V2 的 Gold 推定错误**。建议案例数据用合成内部 ID，不生成看似真实的身份证号码、学籍号或签章。

运行与对照顺序：

1. 独立金标作者先读 I 原文，冻结每案适用条件、有效来源、每个事实的期望状态及**全部** issue，标记 source uncertainty；模板作者不读取 Gold。
2. 在隔离非生产配置与全合成数据下，以真实 D1/D3/D2 产物动态实例化 I01–I16；检查每案 Rule/Check/SourceRef/Subject/版本与 source binding，确认不是固定演示计划。
3. 对能被现有技术可靠表达的用例，实际创建 D2 技术案卷、运行 Pi 服务端受控接口并记录 Case、Run、原始返回、拒止理由与退出码。合成 Pi 回执只证明技术门禁行为；**未真实调用在线模型则 `onlineModelAccuracyVerified=false`**。
4. 与独立 Gold 比对**主状态、完整并发 issue、操作/对象权限、合法替代、生效时点、审批责任**；单独测假阳性误放行、假阴性误补件、错误升级人工、条件未知当不适用。
5. 从公开合成有效案卷复制，仅改变一个字段（owner/verified/version/subject/证据类型/阶段），建立成对的负例与合法例；至少包含一次「合法材料不被误拒」和一次「无权批准不被输出」。
6. 用新隔离配置重导入当前模板，再重新跑关键案，记录结果与 fingerprint；保留所有无法执行/无法比较的测试为 `NOT-RUN` 或 `TOOLING-BLOCKED`，不替补成「模拟 PASS」。

**阶段 2 必交**：合成原始输入、独立 Gold 哈希/隔离证明、每个案例的实际 D2 plan、受控服务端真实 Case/Run 及测试输出、逐案 pass/fail/not-run、误放行和误拒分析、变形测试记录、版本复审结果、独立审查报告。真实用户数据和未经授权校方接口不进入本轮。

## 四、验收门槛与缺陷归因

| 检查层 | 可签的结论 | 不能借此宣称 |
|---|---|---|
| 文档责任完整性 | 原 MD 全责任有明示去向，且有按来源、对象、版本的解释 | 自然语言等价、校规有效 |
| 作者态技术链 | D1/D3 真实建模、版本、导出重导入，D2 按案编译 | 全部条件门禁均生效 |
| 合成服务端行为 | 指定的 D2/Pi 受控技术 Check 和拒止，证据可重现 | 在线模型准确率与正式批准 |
| 独立业务 Gold | 有界合成案逐项通过/失败/待核的完整对照 | 全体实际学生材料准确率 |
| 实际业务上线 | **本轮不签** | 真实校方制度/审批授权 |

**一票阻断技术模板「可以安全全量使用」的情况**：错误扩展另一个学生/字段的证据效力、把未知或权威待核当已通过、自动替代有权审批、跨运行版本静默复用旧结论、偷偷删掉原文关键规则，或高风险错误 `READY`。严重误补件/合法替代错误拒止同样作为 `Major` 单独修复；不可被整体正确率掩盖。实际工具不支持则保留部分可运行、显式范围和 blocker，**可以完成阶段试点工作，但不能签无缺口完整模板**。

**建议并行角色**：
- I **制作 Agent**：只制作自己业务作者态和技术 plan，不可自己修改 Gold、公共引擎或其他模板。
- **独立 Gold/回归 Agent**：基于固定原文、先冻结预期，再看制作产物与真实 Pi 行为；报告模板误建、技术门禁缺口或 Gold 原文歧义。
- **D4 主集成 Agent**：维护唯一 D3-R0 SHA 与公共能力问题票、PR base、集成 CI；不与 I 作者竞争制作同一业务。

归因包括 `AUTHOR_MAPPING`（原文转错）、`DATA_CONTRACT`（字段/枚举/数组认错）、`D3_TOOLING`（真实编译或运行能力缺失）、`GOLD_AMBIGUOUS`（原文/Gold 证据不足）、`POLICY_UNCONFIRMED`（校本现行性不明）、`ENVIRONMENT_NOT_RUN`（没有真实执行）。前两类优先修业务模板与测试，D3 公共缺陷才统一定向修复并另发冻结版本。

## 五、开始条件、完成条件与后续安排

- **开始前**：确认技术固定 SHA、I 原文 SHA、测试隔离、执行环境、独立评测者、Git 分支和 PR base；明确「全部合成」及无学校审批权限。
- **完成第一阶段**：独立提交可复现的 I 作者态与不同条件下的实际 D2 plan、完整责任去向、真实日志和已知阻断。
- **完成第二阶段**：16 个冻结案逐项给出实际证据或保留 `NOT-RUN`，高严重度误送审清零且复测，报告合法材料误拒，Gold 不因作者答案修改；独立签署**限定范围**结论。
- **扩大到其他四套 G01**：由同一次 I 试点的可复现问题决定是否需要轻量修订通用提示词，随后让 A/C/S/P 平行推进；不等每一处校本政策疑问都解决，也不将本试点自动升格 D5。

**决策**：优先做这两项真实工程动作，而不是继续设计离线 V4/V5。若出现实际阻断，优先出最小复现与明确责任归因，不倒退回冗长抽象调研。
