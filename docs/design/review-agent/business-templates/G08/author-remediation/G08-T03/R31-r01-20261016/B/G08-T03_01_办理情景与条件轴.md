## 3. 组合/互斥说明

1. SC01-SC08 主要初次申请；SC10-15 主要原工单后续阶段；SC09、SC17 可组合为多部门/多子问题；SC18 与任意阶段紧急风险共存。`SC16`为排除/分流分支而不是独立申诉实体模板。
2. 不枚举 `12轴×所有值` 的笛卡尔积；只组合有实际办事依据和误判风险的路径。
3. 学校级“建议实名”不能转换成学院级“原则不回复匿名”；`anonymous_frontend=true`不等于`backend_unregistered=true`。
4. `prior_ticket_id`只在再次办理/反馈/撤回/进度查询时要求；首次普通建议中它应该是`N/A`，不是“缺失”。
5. 一封信中两个同类反映可由承办机关分拆子请求，但原学校关于“一信一事”的明确限制仅对实施该限制的渠道启用。

## 4. 业务阶段结果，不要混成通过/驳回两档

| 阶段 | 可判断 | 不可直接判断 |
|---|---|---|
| 新来信收件 | 接收记录、文字存在、是否需要归口 | 投诉事实是否被证实 |
| 受理程序核验 | 该渠道是否面向主体、事实与请求是否足以定位、需要补正的项目 | 有权部门最终认可请求 |
| 承办分派 | 建议交哪个部门、是否多部门协同 | AI直接替代校办签发转办单 |
| 办理及回复 | 可信后台状态、是否已有答复、有没有联系人、敏感信息 | 用户截图证明学校已解决所有实际问题 |
| 再次办理 | 原单关联、评价与继续选项、后续事实、平台当前允许的操作 | 正式信访复核实体结论 |
| 归档 | 回复/转办/结案时间链、授权的实际最终状态 | 将模型审核“合规”当作实际处理已完结 |
### R31-r01 附加办理轮次/时钟语义（B作者、2026-10-16）

首轮`feedback_round=1`在**首次学校处理结果正式反馈**并经可信后台核实后开启评价；用户评分时写评价事件并独立记录`rating`与`continue`。`rating in {一般, 不满意} AND continue=true`且具有原案关联、合法访问/操作权限、F49原因才可**建议**二次上报；只有学校有权平台实际新建且留痕才有第二轮。官方EX01的第7天短信提醒、第10天默认满意办结，均从**处理结果反馈后**起算，不能从点击评价或建议创建时起算。第二轮满意或一般办结；不满意按平台最终反馈，不循环执行首轮R31。以上事件字段属于保守业务模型(S)，不是已经核对的真实数据库字段；成都理工邮箱自动续办能力(U)不得据此外推。
