## 2. 五份完整模板首先暴露的结构差异

| 模板 | 完整审核目的与真正业务对象 | 无法丢失的专属差别 |
| --- | --- | --- |
| **I** | 在籍学生身份登记更正的材料和程序预审；一次申请可修改姓名、证号、出生日期等多个字段，并追踪旧值—新值—更正原因—权威原始登记源 | “合法更名事实”不等于字符串不相等；招生/录取原始数据差错与毕业后历史记录勘误不能归为普通账户资料修改；一份法定文书可覆盖多项更正事实（I §3、§6、§12.1） |
| **A** | 一份申请单 → 0–多主体/授权关系 → 1–多档案件 → 每件 1–多操作；`case_id + item_id + operation_id` 是可追溯键 | 查阅、摘录、复制、外借权限不能互相继承；档案已公布≠档案已开放；操作授权必须匹配对象和范围（A §2.1、§4–6） |
| **C** | 申请人、拟持卡人、关联教职工或责任单位形成一条资格与代办关系；`family` / `temporary_service` 是同一模板的两条分支 | 亲属关系已证不等于有权代办，服务事实已证不等于校方已批准卡资格；在职、离退休、已故等是分支内部条件（C §1、§4–6） |
| **S** | 一份专项用印申请可组合事实证明、制式申请材料、译文、复印/密封与骑缝等不同动作 | 申请阶段后续学校栏位可合理留空；批准稿版本与送印稿版本必须核对，章种/份数/批准范围需要独立绑定（S §1、§7–8） |
| **P** | 政审材料的程序性核验，区分组织出具、收件、签署阶段和责任主体 | 出具端起始材料不应被要求满足收件端完成态；材料形式核对不允许升级为政治、思想或组织实质认定（P §0–2、§5、§12、§14） |

**直接结论：** 目前只有 `case/subject` 的字段作用域不能天然表达 A 的“档案件×操作”，而 C 的“申请人→持卡人→资格关联人/单位”也不等于多个普通字段。短期可把每个 `(item, operation)` 映射到一个有稳定业务键的 `ReviewSubject(type='custom')`，但制作态必须保留原来的角色、对象和关系含义，不能只靠 title 文本。

## 3. 共性能力矩阵：哪些是基础设施，哪些可能是真模块

标记：**●** 源文档明确要求；**◇** 有相近场景但不能直接证明同一局部语义；**—** 现有材料不足以视为核心共同需求。下表是**需求对照**，不表示代码已实现。

| 审核表达能力 | I | A | C | S | P | 建议归属 |
| --- | :---: | :---: | :---: | :---: | :---: | --- |
| 明确审核目的、适用和排除边界 | ● | ● | ● | ● | ● | 完整模板及路由卡元数据 |
| 适用学校/身份/时间/阶段和政策确认状态 | ● | ● | ● | ● | ● | **基础规则治理** |
| 条件组合、互斥、三值 unknown | ● | ● | ● | ● | ● | **基础条件引擎** |
| 用户自述与可信系统/授权人事实分离 | ● | ● | ● | ● | ● | **基础事实来源** |
| 证据按“证明哪个事实”关联、AND/OR 与替代 | ● | ● | ● | ● | ● | 基础证据关系 + 局部业务模块候选 |
| 多主体、委托、代理与权限范围 | ◇ | ● | ● | ● | ● | **业务模块候选**，实体权限专属 |
| 有效期/请求期间/批准范围对照 | ◇ | ● | ● | ● | ◇ | 受控比较原语 + 业务模块候选 |
| 当前阶段是否要求某材料已存在 | ● | ● | ● | ● | ● | 基础责任与阶段条件 |
| 跨材料冲突、历史版本与原件来源 | ● | ● | ● | ● | ● | 基础比较/溯源能力 |
| 多对象/逐操作局部结果、主状态聚合 | ◇ | ● | ◇ | ● | ● | 基础对象/结果模型 |
| 人工正式决定与 AI 预审分离 | ● | ● | ● | ● | ● | 基础工作流及授权约束 |
| 独立测试预言、失败与反误杀覆盖 | ● | ● | ● | ● | ● | 制作工具测试能力 |

**重要防误抽：**
- “五份模板都要核对姓名”只能直接支持**字段/来源比较能力**，不能把姓名匹配抽成能够证明政审、查档、发卡或用印资格的万能业务模块。
- “五份都涉及政策版本”应先建立**政策适用性治理**，不是允许任意模块按严格程度求并集。
- “材料槽为空”不等于“该事实无法证明”；OCR 不可读也不等于未上传。
- 各文档自列的 `M01/Mxx` 多数是作者对**编辑器共性机制**的建议编号，并不都符合第 15 号规范对**可复用业务模块**的语义完整性要求。

对应证据：I §4–6、§12；A §2–5、§11–12；C §3–6、§11；S §2–4、§17；P §3–6、§16。

## 4. 分三层抽取，而不是把规则列表拆成模块列表

### 4.1 基础能力（How）：编辑器/引擎应共享，不做业务模块货架

| 代号 | 建议先有的表达/治理原语 | 不可违反的边界 |
| --- | --- | --- |
| A01 | 业务对象类型、角色、稳定 ID、字段作用域与关系 | 上传者、发起人、被审核人、受益人、授权方可不同 |
| A02 | 声明事实、系统可信事实、人工事实与出处 | AI 抽取不自动变成权威登记/有效批准 |
| A03 | 条件 AST 和 tri-state 适用性 | 未知不得当假；不适用不代表不符合 |
| A04 | 政策来源、学校/角色/时期/阶段匹配、版本与确认态 | 未证实校本强制规则不能据外校示例补齐 |
| A05 | 待证事实（Claim）、材料证据与主体/操作的多对多绑定 | 一证可多用，复用附件**不复用授权结论** |
| A06 | AND/OR 替代证据、阶段性必需与提供责任方 | 系统内部状态不能误记为学生未上传 |
| A07 | 有限数值、区间、集合、版本比较及出处定位 | 比较器不能推导法律效力或真实签章权限 |
| A08 | 局部结果、问题代码、未知/未读/失败区分与聚合 | 多个问题不能被一个“通过率”覆盖 |
| A09 | 版本快照、来源映射、差异预览与独立回归测试 | 不修改历史模板/案卷的真实口径 |

这些是“五套真实模板能被正确制作”的**前提能力**，未必需要全部做成新的包或 GUI 组件。

### 4.2 复用业务模块（What/Why）：本轮只提出四个候选

| 候选 | 局部审核目的 | 横向证据 | 不能顺带批准什么 | 推荐 |
| --- | --- | --- | --- | --- |
| **B01 有权代办与授权范围核验** | 代理人/经办人是否有权针对**特定对象、操作、期间**办理本次事项 | A §2、§12；C §4/§11；S §17；P §2/§16 | 不能把“委托关系成立”当作档案开放、发卡资格、章权或政审合格 | **第一批试点** |
| **B02 待证事实与证据链覆盖核验** | 指定事实是否获得允许来源的充分、互补或等效证明，并定位缺口 | I §4/§6/§12；C §4/§11；A §4/§12；S §17 | 不得自行认定等效证据法律效力或校方认可范围 | **第一批试点** |
| B03 资格/批准有效期与请求区间 | 已生效的资格/批准是否在限定条件下覆盖请求的时段 | C §4–6；A §4/§6；S §8 | 不把续期“申请中”当“已生效”，不生成全校统一最长期限 | **候选，暂不抽库** |
| B04 制式栏目阶段责任核验 | 特定阶段哪些栏位应由何种角色完成，哪些当前合法留空 | S §1/§7；P §5/§12；A §4 | 出具阶段不要求收件终态签字；图片有印 ≠ 真章授权 | **第二波候选** |

**提取门槛：** 一项模块必须在两套以上真实模板中有**相同的局部目的、输入范围、可解释输出和例外**，且重新组合后原模板反例不变。B01/B02 目前仍是**候选**，不是可发布已验证模块。对复用收益不明显的项应保留在模板内部，避免为了模块数量牺牲正确性。

### 4.3 不能跨模板继承的专属业务语义

- **I**：依法更名的旧新关联、身份证号码纠错与格式转换、原始招生记录错误归因、毕业后历史注册勘误（I §6、§12.1）。
- **A**：档案开放/公布/限制状态、档案件×操作×授权范围、原件外借和归还责任（A §2、§12.2）。
- **C**：认可亲属范围、已故/退休教职工资格路径、挂职/派遣/长期服务卡别与特定办卡许可（C §4–6、§11.3）。
- **S**：批准稿与送印稿比对、章种/份数/用印对象绑定、骑缝与密封、真实 OA 与现场用印执行（S §7–8、§17）。
- **P**：受理/出具端责任区别、正式组织意见、政审敏感事实及其不得自动实质认定的边界（P §0–2、§14）。

基础比较能力可以复用，但**业务解释、校规参数和有权决定权**不得随着模块静默传播。

## 5. 对照当前代码：能力在哪里、真正缺什么

静态检查的是仓库 `main`，不是用户应用现场测试。

| 现有能力 | 已在代码中看到 | 五模板提出的缺口 / 危险假设 | 优先 |
| --- | --- | --- | --- |
| 模板身份与冻结 | `TemplateVersion.templateId/version/status`；`template-store.ts` 草稿、发布及校验 | 作者态缺模块实例版本、来源映射和变更影响；不能靠目录编码充当稳定主键 | P0 |
| 字段与条件 | `FieldSpec.scope='case'|'subject'`、`conditionRequired`；`ConditionAST` + `TriState` | A 的 relationship/item/operation，C 的资格多主体关系无法按有语义的对象角色完整建模；AST 没有自带权限范围/证据链运算 | P0 |
| 材料槽 | `MaterialSlotSpec.requiredWhen/requiredAt/minCount/maxCount/allowReuseAcrossSubjects` | 当前槽不能完整表达 `Claim ↔ (Evidence AND/OR) ↔ 业务对象/操作范围`；`requiredAt` 仅 `submission/decision`，不覆盖全部实际阶段 | P0 |
| 审核标准与规则 | `TemplateSectionSpec.criteria: TemplateCriterionSpec[]`；另有 `PolicyVersion.rules: RuleSpec[]` | **编辑器标准与完整规则能力不对等**：criterion 没有 `when`、权威政策引用和 `onUnknown` 等；需要明确编译/绑定关系，否则界面看到与运行生效可能不一致 | **P0 最高** |
| 运行对象 | `ReviewCaseV2.subjects`、`ReviewSubject(type='custom')` | 可临时把 A 每个 `(itemId,operationId)` 映射独立 subject，但需要结构化业务键，不能只存标题或合并操作授权 | P0 |
| 工作流 | `WorkflowStageSpec` 含阶段与 `enterWhen/exitWhen` | 编辑器 `linkedStages` 目前会按顺序生成 `nextStageId`；组合/回退与审批责任需要更精确的作者模型，不能视为全部完成 | P1 |
| 规则来源 | `policyRefs`、`RuleSpec.confirmation`、`sourceRefIds`、政策 hash 校验 | 须在作者界面把“校本已证/跨校参考/待核/设计/模拟”和适用范围及权限分开表达，不让模型自动升级为正式校规 | P0 |
| 静态校验 | `validateEditor` 和 `validateTemplate` 可查部分 ID、空值、字段/槽位引用、阶段、政策引用等 | 尚无模块版本/依赖/参数、业务冲突、跨校误继承、完整证据覆盖与源规则映射验证 | P0/P1 |
| 编辑 UI | `TemplateWizardPanel.tsx` 提供字段、分项、材料槽、规则文本、流程、输出、保存发布 | 不能把“有 GUI 编辑表单”误认成支持五套完整 MD；也不必推倒重写 | P1 |

**必须单列两个风险：**

1. `TemplateCriterionSpec` 与 `RuleSpec` 是两种不同的数据表达面。首版作者态必须把每项**规范化审核命题**绑定到实际生效 `RuleSpec`/criterion、PolicyRef 和来源片段，防止“编辑器要求”与“运行中 Agent 收到的有效要求”分叉。
2. 现有空白模板初始化中 `outputs` 可能带 `approval` 输出类型，但五套文档主要是**材料/程序预审**。显示“审批结果”不应意味着 Agent 自动拥有学校审批权限；必须在编辑器中明确可输出意见和有权执行动作的区别。

这一判断不是要求立刻替换所有运行模型。相反，现有 `TemplateVersion`、`RuleSpec`、`PolicyVersion` 和 Pi 服务已提供宝贵基座，**先补足作者态所需的语义，再决定哪些运行结构确实需要向后兼容地扩展**。

## 6. 首版设计建议：制作态独立、运行态固定

```text
完整 Markdown 研究资料 / 作者录入
                 │
                 ▼
    TemplateAuthoringSpec（草稿）
 ├─ 模板目的、适用/排除与路由卡
 ├─ BusinessObjectRole / 多主体关系
 ├─ FieldSpec / ClaimSpec（待证事实）
 ├─ EvidenceRequirementSpec（AND/OR/替代/范围/阶段）
 ├─ ApplicabilitySpec（学校/条件/时间/来源）
 ├─ 专属规则 + ModuleInstance 引用
 ├─ 责任/阶段/局部输出/禁止动作
 └─ Markdown 来源映射 + TestContract
                 │
                 ▼
 Module Resolver / Template Compiler
 ├─ ID / 版本 / 参数 / 依赖与冲突
 ├─ 学校制度适用、三值分支、证据责任
 ├─ 规则与证据目标映射，生效检查预览
 └─ 生成固定版本 + hash / provenance
                 │
                 ▼
  现有 TemplateVersion / RuleSpec / PolicyRefs
                 │
                 ▼
         现有 Pi 审核执行服务
```

以上命名为**概念契约**，不是已确定的 TypeScript schema。优先让作者态独立保存草稿/来源映射，再编译成当前运行结构能够消费的平面生效快照；遇到不能无损表达的内容必须报错或保留“无法映射”，**不能静默压扁为自由文本并假称已验证**。

### 6.1 作者态最少需要回答什么

- **业务是谁**：独立审核目的、适用学校/主体/阶段、业务对象、关系和操作身份键。
- **事实是什么**：待证事实的作用对象、值来源和可信等级；用户声明与后台真值不得相互覆盖。
- **证据证明什么**：每种来源覆盖哪些 Claim，有无互补/替代，何阶段才要求，缺谁提供的材料。
- **规则为何生效**：真实校本政策、外校参考、设计建议、未确认、测试模拟各自的来源和适用范围；未知如何处理。
- **规则怎么执行**：触发、局部动作/结果、失败/未知/不适用、人工权限、跨规则冲突与例外。
- **如何回归**：原始 MD 章节位置、模块实例来源、独立测试预言、版本变化和影响范围。

### 6.2 三种组合操作仍不变

保留第 15 号文档确定的**新增 → 受控参数化 → 有权显式替换**。不允许自由规则继承、默认“从严”、不明来源优先级、任意脚本修改或把一个模板内 28 条规则强拆成 28 个微模块。

### 6.3 B01 模块实例示例（非可执行正式合同）

```yaml
moduleId: review.delegation-scope
version: candidate-0.1
purpose: 核对有权代办关系是否覆盖本次对象、操作和期间
inputs: [applicant, represented_subject, requested_object, requested_operation, requested_interval, authorized_sources]
appliesWhen: {field: is_proxy_application, op: eq, value: true}
policyParameters:
  accepted_authority_sources: "必须由有权模板/校规配置"
checks:
  - 代理或单位经办关系是否有可信证据
  - 授权对象、办理动作、有效期间是否涵盖本次申请
outputs: [delegation_supported, scope_conflict, evidence_unknown]
onUnknown: awaiting-confirmation
limits:
  - 不判断档案是否开放
  - 不判断校园卡资格是否最终获准
  - 不代替章权或政审组织正式决定
testCases: [合法且覆盖, 仅查阅不含复制, 委托已过期, 上传自述冒充授权]
```

B02 同理，但它的输出是“指定事实的证据覆盖状态”而非“这份文件有效所以整案通过”；I 的“一份文书证明更名和更号”必须保存两条 Claim 关联，C 的派遣关系需要按 AND 组成且能由一份涵盖全部内容的可靠来源共同支持。

## 7. 首版编辑器界面：加七个工作区，不画万能节点图

| 作者工作区 | 必须可见和可改的核心内容 | 复用现有界面 |
| --- | --- | --- |
| 业务目的及边界 | 标准目的、适用/排除、路由卡元信息、学校/身份 | 扩展模板基本信息 |
| 对象、角色与事实 | 业务对象、关系、稳定业务键、字段与待证事实 Claim | 扩展字段/分项 |
| 材料及证据链 | 槽、证据来源、证明目标、AND/OR、替代、阶段与责任方 | 扩展材料槽 |
| 条件和规则 | 适用条件树、唯一有效规则绑定、政策来源、未知行为与例外 | 扩展规则区 |
| 业务模块 | 仅已验证模块列表、版本、实例参数与边界 | 增加模块卡片/参数面板 |
| 阶段、结果与授权 | 预审/部门决定/执行责任、局部输出、禁自动动作 | 扩展流程与输出 |
| 生效预览与回归 | 选一个模拟场景，显示哪些规则生效、缺什么、依据为何、哪些待核 | 新增预览与测试面板 |

**“预览”比“拖拽”优先级更高。** 编辑器需要直接展示：选定学校、申请身份、办理动作、阶段和政策版本之后，哪些规则**适用 / 不适用 / 未知**，哪些材料在**当前阶段**必需，哪条来源支持这个要求，为什么某项结果必须交给有权人员。

例如可以先用 C 的 `family + deceased` 和 A 的 `same item + view/copy` 压力测试；S 的批准稿版本变化和 P 的出具/收件阶段差异用于第二批。

## 8. Markdown 辅助导入不能变成“一键自动发布”

五份文档的章节顺序并不一致（I 的 §12、A 的 §12、S 的 §17、P 的 §16、C 的 §11 才是专门给编辑器的抽象建议）。首版不应假设每份 MD 第 N 章含相同数据。

应依次进行：标题/表格/规则 ID 和出处定位 → Agent 辅助候选映射 → 未映射内容单列 → 作者核实业务边界、政策适用和强制义务 → 生成草稿 → 静态审计 → 生效预览 → 测试 → 发布。

**导入率高不代表语义正确。** 保留源文件名、章节/行范围、原文摘录、判断状态；无法可靠映射的复杂关系必须报告出来，不能丢弃或擅自转换为“需要上传附件”。

## 9. 五套模板反向验证测试合同

以下是**需实现/执行**的验收点，不是本轮已跑通过的测试：

| 编号 | 样本 | 要求保持的语义 |
| --- | --- | --- |
| G01-01 | I：旧身份证合法收回，新旧姓名由权威文书关联 | 不机械强制旧证件扫描；合法替代可被核验 |
| G01-02 | I：一份文书同时证明更名及更号 | 两个 Claim 都有独立覆盖，不能重复索取证明 |
| G01-03 | A：同一档案件申请查阅和复制，委托只覆盖查阅 | 查阅与复制独立结果，禁止跨操作继承授权 |
| G01-04 | A：档案目录可见、真实开放状态未知 | 不把已公布当已开放，等待馆方可信来源 |
| G01-05 | C：关联教职工已故，申请人代理资格未知 | 不把非在职视为完全无资格；关系与代办权限分别判断 |
| G01-06 | C：派遣协议存在，但具体人员—接收单位链接不足 | 服务事实和个人资格不能因为有合同就自动通过 |
| G01-07 | S：申请阶段制式表后续签章栏留白 | 不把未来有权部门的签章当提交者缺件 |
| G01-08 | S：获批稿与待印稿版本不符 | 旧批准不自动覆盖变更的用印对象、章种和份数 |
| G01-09 | P：处于政审出具阶段，不是收件完成阶段 | 不提前要求接收端最终完成态签章 |
| G01-10 | P：材料仅支持形式检查或敏感事项无法确认 | 不做政治/思想实质裁决；需要有权人工复核 |
| G01-11 | 任一：校本细则未知，只有外校案例或模拟规则 | 不自动成为本校刚性拒件依据；保留政策待核 |
| G01-12 | 任一：材料 OCR 失败、几项问题并存 | 保留未读、冲突、缺证和局部检查；不汇总成“已通过” |
| G01-13 | 原模板 → 作者态 → 模块化 → 固定运行快照 | 逐条比较有效规则、触发、范围、出处、角色、人工边界和正反例 |
| G01-14 | 模块/校本规则版本变化、材料替换 | 历史快照及结论不被静默改写；新运行有影响范围和差异 |

测试预言必须与 Agent 待审材料**分开存放**。首先需要把原 Markdown 的规则整理成可追溯的结构化基准，之后才谈“模块化前后等价”；不能直接拿模型对原 MD 的自由回答当金标。

## 10. 建议开发顺序

| 阶段 | 交付物 | 验收边界 |
| --- | --- | --- |
| **D0：本轮完成** | 五模板差异/共性、分层模块候选、代码缺口、验证合同 | 仅研究结论，不声称模块已可用 |
| **D1：作者态数据契约** | 最小 `TemplateAuthoringSpec`、业务角色、Claim、证据关系、规则来源映射，及与运行态的编译协议草案 | 每一条关键业务语义有明确承载位置；不允许埋在提示词里 |
| **D2：先做一套模板无损映射** | 优先 C 双分支，补 A 的 `item×operation` 边界压力测试 | 能显示生效/未生效/未知规则与待证事实，不把来源待核写成必交 |
| **D3：两模块抽取与反向重组** | B01、B02 模块实例，C/A/I 跨模板比较与回归 | 模块版本/参数/权限、反误杀、证据覆盖未退化 |
| **D4：其余模板覆盖测试** | S 的用印批准稿版本/阶段，P 的出具/收件和敏感边界 | 五套在统一有效快照与独立金标下可比 |
| **D5：编辑器增量 UI** | 条件组、事实/证据关系表、模块实例、来源、场景预览和测试 | 复用 `TemplateWizardPanel`，不做任意节点图或平行审核引擎 |

**P0 工程风险是“规则的双重真相”：TemplateCriterionSpec 与 RuleSpec 如何明确一一映射，谁是最终的唯一有效要求。** 这个问题应在 D1 优先解决，否则模块组合器即使做好也可能编译出与界面描述不一致的审核任务。

### D1 仍需专门讨论的选择

1. 作者态是否使用独立关系结构，怎样无损映射到现有 `ReviewSubject`；
2. Claim/Evidence 多对多及替代条件最终如何落在运行态，如何保留来源与作用对象；
3. `TemplateCriterionSpec` 与 `RuleSpec` 的唯一可信表示、规则版本与编译映射；
4. 阶段要求超出 `submission/decision` 时如何兼容扩展；
5. 模块参数的校本授权与冲突规则，何种不确定性禁止发布；
6. 各份 MD 的源段映射与已完成离线测试包是否能够实际拿到、运行。

## 11. 最终判断

**现在可以开始设计模块化模板制作工具，而且它比立刻扩张 Jev 自动路由更适合作为下一阶段的主任务。** 模板路由可以读取本阶段产出的目的/适用/排除元数据，但不应要求路由 Agent 临时理解业务模块并组合规则。

首批真正要验证的**业务模块候选只有 B01 和 B02**；政策来源管理、条件树、材料出处、角色关系原语、对象/操作粒度应作为**共同基础能力**。先完成 D1 的表达模型，再通过 C 和 A 的复杂场景检验，不必一开始就建设一个涵盖上百套模板的“万能模块商店”。

核心目标与第 15 号规范一致：**先有完整且可追溯的业务模板，后抽取跨业务仍语义稳定的局部模块；制作平面允许组合，运行平面只消费冻结后的生效审核要求。**
