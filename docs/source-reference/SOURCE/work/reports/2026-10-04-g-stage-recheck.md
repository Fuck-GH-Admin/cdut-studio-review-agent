## 1. 结论

**这轮有可验证的进展：V2 能重新打开已有案卷、登记真实文件，补件回复能落盘，判定满足后能重建任务；评分和离线回复也增加了真实事务。完整本地通用审核 Agent 仍未闭环。**

最核心的缺口仍是“提供规则与材料后，Agent 实际执行审核”：V2 运行通道没有接到产品，Pi 执行器没有使用材料和返回结果，OCR 仍无可用实现。配置模板后也不能从该模板创建案卷。普通用户即使知道使用方法，仍无法完成目标中的完整单案、独立评分、批次和副本往返。

这不是商业化权限或学校 API 的要求。本地执行器、模板使用入口、补件再次提交、评分轮次、离线回复应用都属于当前产品应实现的业务。校方身份、资料核验和结果回写继续单独按 S 类验收。

本次修复了提交中断、自有规则丢失，并隔离案卷切换时的姓名输入；没有把其余功能缺口改成通过。下一轮优先接通一份真实材料的 V2 单案，再扩展六模板、批次和独立副本。

## 4. 本次已修复

### F06 · 提交在登记材料后冲突，并留下无任务的 submitted 案卷

实际路径：打开 draft 案卷 → 登记文件（revision 变 2）→ 提交。提交命令先写为 submitted/r3，随后 `ensureInitialTask` 按固定 expectedRevision=0 建任务，收到 revision 冲突。落盘是 submitted、documents=1、tasks=0，重开后无法再提交。

`stage-workflow.submitCaseV2` 现在把状态和首阶段任务放入同一个聚合事务；成功重试复用回执，不增加 revision 或任务。旧版留下的 submitted/无任务案卷可用面板“恢复审核任务”恢复，本次实测 r3→r4、开放 auto-check(R1)、原件保留。

新增三个 BDD 行为回归覆盖非零 revision 正常提交、旧中间态恢复、成功提交重试，修复前全部失败，修复后全部通过。**这只解决提交的原子性；当前提交仍未使用模板必需槽位门控，不能据此宣称材料完备。**

## 5. 仍然阻断完整使用的事项

P1 表示会阻断业务、丢输入或产生错误结论；P2 表示用户缺少配置/恢复/查看入口。两类都保留在完整交付范围。以下按当前产品调用链判断，不把旧实现的错误直接套到新增服务上。

### 5.1 G01/G02/G12 · P1 · V2 实际审核尚未执行

- `RUN_REVIEW_V2` 仍只有共享常量，没有 handler、preload 方法或按钮；`runReviewCaseV2`、`buildReviewExecutors` 和 `runBatchQueue` 没有产品调用者。
- `pi-review-executor.ts` 的提取/语义核对 Prompt 只有节点 ID/hash；没有案卷材料与规则。工具只是名称字符串，没有实际注册。`complete` 返回内容未使用，固定返回空 observations/opinions。
- `NullOcrPort` 仍是当前 OCR 实现。没有实际 Tesseract 适配/worker/语言资源。资源自检仍将 OCR 标 deferred、解析 available 写死，不能据此证明随包可用。

**下一步：** 在共享契约→main→preload→renderer 四层接通同一 V2 运行；复用现有 Pi、模型设置和解析基座，装配完整材料/规则输入、可调用工具、结构化结果与引用验证。先验一份符合案、冲突案、失败案，再验补件后增量重审。实际模型质量和目标机资源测试建立在实现之后。

### 5.2 G03 · P1 · 新校验没有接到入口，事实仍不统一

`review-ipc.ts:244` 调用 `updateFields` 没有传入模板。按该入口相同调用形式更新 declaredScore=0，落盘为 `{kind:"text",value:"0"}`。显式传模板时，校验器把未声明 scope 当 case，而创建器当 subject，内置事项数字字段反被拒绝。日期 `2026-99-99garbage` 也通过了日期前缀检测。

确认观察为 number 7 后，观察值是 7，事项表单值仍为 text 0；绑定不存在的材料版本与外案事项仍 accepted。事实/表单/运行输入不能各自成为独立真值。

**下一步：** 所有创建/更新从锁定模板读取 schema；统一 scope 默认值和 FieldValue 类型，校验真实日历日期、枚举及有限数。定义人工确认值优先级，将观察纠错和证明绑定验证纳入同一聚合命令及输入指纹。

### 5.3 G04/G05 · P1 · 补件不足后不能再交，阶段决定缺业务门控

新任务回流的正常路径已通过，但反例仍存在：

1. responses=0 也能判 satisfied，并产生开放任务。没有明确的材料豁免动作。
2. 回复后判 insufficient，再次回复返回 INVALID_TRANSITION；同时 insufficient 没有计入未满足门控。
3. student actor 可以推进 system 的 auto-check 任务。这里要求本地动作与工作角色匹配，不是在要求学校账号平台。
4. 事项决定仍写 case scope；同任务第一次事项决定后，下一事项被去重拒绝。决定 `basedOnRunId=run@revN` 不是实际运行引用。
5. 申诉维持/更正后仍为 in-review；更正继承原决定 actor，缺少明确提交/闭结 UI。

**下一步：** 不足保持可回复和阻断续审；判满足必须基于有效回复/核验或明确豁免；取消的请求按整体门控恢复。任务角色、事项范围、轮次、有效运行和申诉最终投影按同一命令合同验证。UI 必须允许填写说明、上传附件和查看回复，不再使用固定“已补交材料”文本代替真实提交。

### 5.4 G06 · P1 · 评分未按任务与轮次闭合

本次直接检查新增 `rating-service`，未将旧 `judging-service` 的所有反例当作新服务结果：

- student actor、不存在的 stage、ghost 维度 9999 分仍可 accepted；有限数校验不等于量表范围/分配验证。
- R1 的 j1 与 R2 的 j2 被一起汇总，有效人数 2、无 blocker；查重键也不含轮次，重开后同人合法新评分会被拒。
- 仅一人而最低两人时，有 blocker，但 average 仍为 4。若保留预览均分，需要明示未达到定稿条件，全部输出与定稿共用该条件。
- 没有独立评委分配与可填写量表的完整页面；当前快捷评分写固定 overall，不能替代任意模板量表。

**下一步：** 唯一当前票按 case/stage/assignment/actor/round 定义；命令验证量表和工作权限，汇总明确过滤轮次。缺评/N-A/最低人数、同分和名额进入定稿门控；两套评分基础合成一条产品路径。

### 5.5 G07/G08 · P1 · 第二次离线回复冲突，附件可“成功但未应用”

第一包 accepted、同包重复 duplicate 已真实改善。然而同一学生导入第二个合法包，即使 packageId 不同，只要案卷和 actor 相同，命令仍使用固定 requestId，第二次新说明被拒绝为“同 requestId 不同载荷”。若说明相同只换附件，返回 accepted，但 responses 仍只有第一包 d1，没有 d2：附件未参与命令 payload hash。

重复成功包修改 projection 标题后，因只比较 replyHash，在完整包 hash 校验失败之前就返回 duplicate。基准 revision/任务/轮次冲突也未完整校验。离线补件应用绕过正常回复命令的状态校验。

新增往返 outbox 会先存 pending；旧 `pushViaOutbox` 仍在端口响应之后落盘，本次延迟响应探查确认 pending 不存在。两者都缺完整可重放载荷与启动恢复循环，不能把新增文件等同于可靠中断恢复。

**下一步：** 传递真实 packageId/actionId 与完整命令载荷（含附件版本），先校验完整包及基准版本，再做持久幂等；线上/离线共用补件与评分命令。补件附件随包携带、登记且校验归属。发送前保存完整动作，恢复 pending 并验证接收后回执丢失情形。

### 5.6 G09 · P1 · 公开报告与包投影没有共用输出策略

`projectForRole` 仍将真实 title 与全部 decision.reason 交给评委；ownRating 取 dispositions，而不是新 ratings。新 `buildPublicReport` 排除 internalNotes，却原样输出 decision.reason：将内部调查细节放在决定理由中，学生公开报告仍出现该内容。独立报告函数也没有产品调用者。

**下一步：** 明确公开反馈与内部决定理由的字段/可见性，共用一套投影用于页面、报告、包；匿名覆盖标题、正文、附件和身份映射。本地工作视图与校方身份权限继续分别验收。

### 5.7 G10 · P2 · 发布后仍不能使用模板建案

规则文本输入可用且本次已修丢失，但编译出的语义规则没有真实来源锚点和负责人确认流程。向导仅提供固定 auto-check→first-review→可选 rating→final-review，没有条件/公式/流程/输出编辑或试跑。发布成功文字说“可在创建案卷时选用”，实际建案仍硬编码 comprehensive-assessment-v2；当前没有对应选择器。

**下一步：** 先完成模板列表/使用模板建案、字段和材料槽动态表单、真实规则来源与试跑，再逐项补编排。至少从 UI 建成第七个业务，提供自身规则，完成同一案卷的补件与终审，不能只验保存 JSON。

### 5.8 G11 · P1/P2 · 队列函数存在，批次产品仍无法启动

实际点击创建，面板仍显示固定 `case-rt-1 — queued`，当前隔离配置不存在该案卷，也没有启动/重试/分配评委的按钮。服务 `runBatchQueue` 调用前未提供 runCase 时，先把状态写 running 再报错，落盘留下 running。

**下一步：** 创建时核验真实案卷和版本锁，允许选择/分案；队列调用已接通的单案服务，启动前验证执行器，区分待人工/失败。具备暂停、重试、列表恢复、当前轮评分矩阵与定稿快照。不能通过手动把 queued 改成 done 演示闭环。

### 5.9 G01/G13 · P2 · 材料与工作恢复仍难使用

V2 登记固定 role=evidence、无 materialSlotId，页面不显示已登记文件、解析状态、预览或槽位分配。submit 只判断 documents 非空，没有调用已有必需材料检查。同名上传每次新 documentId，没有真实 supersedes 引用，不能把 active 标记当完整版本链。案卷列表在补件动作后还显示旧 submitted/r4，而详情已经 reviewing/r7；重新打开才刷新。

重启能打开案卷是实质进步，但批次列表、已发布模板使用、未发布向导恢复仍缺。顶部导出/助手也仍读取 V1 上下文，用户在 V2 工作页容易操作另一案数据。

**下一步：** 材料表、槽位、必需项、预览和版本链与动态表单一起实现；案卷变更后统一更新摘要和当前选择。顶部动作绑定当前工作对象并显示对象，草稿/模板/批次按现有本地配置仓库恢复。
