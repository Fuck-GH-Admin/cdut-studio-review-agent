# CDUT Studio 内容审核专区：完整产品设计与现状分析

> 更新：2026-10-01。主项目是 CDUT-Studio，CDUTServer 仅作相关项目参考。审核对象首先是学生综测申报与各种活动申请，也包括其他需要“依据—申请—证明—审批”的材料。当前学校不能提供真实审核 API、页面或案卷；若评审通过，产品还应接入学校系统。因此，文件导入是现在可用的案卷来源，校方接入是同一产品的另一种来源，三栏体验和审核逻辑保持一致。本文定义产品应具备的能力及验收结果，不规定开发顺序。文档尚未对应已完成的产品代码。（2026-10-02 注：本设计已实施落地，现状见 `docs/plans/2026-10-02-content-review-demo-implementation.md`、`docs/plans/2026-10-02-content-review-generalization.md` 与 `work/reports/2026-10-02-acceptance-report.md`；本文其余“尚未对应产品代码/当前无审核案卷”等表述均为写作时点事实。）

## 1. 产品定位与最终形态

内容审核专区是一套**可解释的材料审核工作台**。它把申请事项、证明材料和适用规则对齐，先由 AI 审核员生成逐项结论和修改建议，再由有权限的人确认、补件或作正式决定。学生可以用它在提交前自查；辅导员、学生组织和审核老师可以用它审材料；接入学校系统后，它还可以读取正式申请并回写经人工确认的审核结果。

一个案卷至少包含：审核类型、申请人、申请事项、证明文件、适用依据、审核记录。综测案卷的一份申报表可能有多条加分项；活动案卷可能包含申请书、策划书、预算和活动证明。两者都用“**事项 → 证据 → 规则 → 发现 → 人工决定**”表达，差别交给审核模板和规则包处理，不另造一套界面。

用户能清楚看出三类信息：

- **原始事实**：文件中的原文、表格单元格和图片区域，以及校方系统提供的原始字段。
- **机器解释**：AI 提取的规则、申报字段、证明事实、关联关系和审核建议。
- **人工决定**：用户修正的字段、补件要求、复核记录，以及在有校方授权时形成的正式审批结果。

AI 审核结果不自动成为学校的正式决定。当前无接口时，工作台完整支持本地案卷、人工复核及导出；有接口后，在同一案卷上增加校方身份、状态同步和正式提交。

## 2. 从进入页面到完成审核

1. 用户新建或打开案卷，选择“综测加分”“活动申请/材料”或“自定义审核”。案卷可来自手工上传、演示样例，未来也可从校方系统同步。
2. 左栏导入本案适用的校规、综测细则、活动通知或材料清单。系统生成规则大纲，用户确认适用学年、发布单位、版本与优先顺序。
3. 中栏导入申报表和多份证明。系统列出**所有成功识别的可审核事项**，将证明初步关联到事项，并把未识别和未关联材料显式列出。用户可以修改字段和关联关系。
4. AI 审核员按事项核对规则、申报与证明，给出建议分数或审批建议、问题卡、缺件清单、未覆盖内容和总览摘要。
5. 点击问题卡时，左栏跳到校规原文并蓝色高亮，中栏跳到申报错误或证明位置并红/黄高亮。用户可追问助手、修正材料、要求补件、重审。
6. 审核人记录人工决定。当前形态可以生成预审/复核报告并导出；未来接入校方系统后，具有相应权限的决定可按校方流程回写并同步状态。

这些步骤对学生自查和老师复核使用同一页面，按钮与可见状态随角色变化。学生不能把自己的 AI 建议标成老师批准；老师的正式决定也不能由模型自行代签。

## 3. 三栏工作台

| 左栏：审核依据 | 中栏：申请与证明 | 右栏：AI 审核员 |
| --- | --- | --- |
| 上传或选择依据包；显示来源、版本、适用对象和学年。 | 上传或同步申请表、附件、图片及材料包；按事项整理。 | 显示审核覆盖、建议处理、建议分数、问题卡与待人工复核列表。 |
| AI 生成可展开的规则大纲：准入条件、指标分类、等级/分值、材料要求、时间范围、上限、互斥、例外。 | 展示申报字段、原文位置、绑定的多份证明、从证明提取的事实；未关联文件另列。 | 每张卡显示问题类型、严重程度、申报事实、证明事实、依据原文、修改/补件建议。 |
| 每条规则可回看 PDF 页、正文段落或表格单元；用户可修正解释、禁用误提取规则，原文保留。 | 用户可改正 OCR、手填遗漏事项、重新分组证明；人工值和机器值有来源标记。 | 允许查看证据、标记误报/已处理、发出补件、人工复核、重审及查看历史结果。 |

### 点击问题卡的联动规则

- **明确冲突用红色**：例如申报一等奖，证明为二等奖；中栏先定位申报等级，用户可切到证书上的等级区域；左栏定位等级与分值条款。
- **缺件或不确定用黄色**：缺证明时定位事项的空证明槽，不伪造文件坐标；OCR 不清时定位原图并提示人工查看。
- **依据原文用蓝色**：左栏定位主条款，若问题涉及多条规则，可逐条切换。
- **定位精度可降级**：表格以单元格、PDF 以页内区域、文本以段落、图片以矩形定位；解析器只能给出文件或页时，明确显示“仅定位到此文件/页”。
- 三栏各自滚动。点击卡片触发左中两侧滚动和短暂高亮；窄窗口可切标签，但从任一出处能返回问题卡。

### 审核助手

右栏按钮及快捷键唤起对话抽屉。它带入当前案卷、选中的事项与问题卡、已确认的规则和出处，回答“为什么这样判”“我要补哪张证明”“申报分值怎么改”。回答引用本案材料；没有依据时说明无法确定。助手可建议操作，实际字段修改、补件请求和审批由用户确认。更换案卷时对话上下文隔离。

## 4. 审核对象、规则与结论

### 4.1 综测

每条申报至少可记录申请人、学年、指标类别、项目/活动、角色、奖项等级、日期、申报分数及证明列表。审核检查：材料齐全性、姓名/学号/活动/日期/等级一致性、适用时间、分值或上限、同一证明是否涉及重复计分，以及例外条款。证明可以包含证书图片、通知截图、组织方证明、签到或公示材料。一条事项可有多份证明，一份证明也可能被多条事项引用；“重复引用”本身不是违规，只有明确互斥/不得重复计分的规则才能给红卡。

### 4.2 活动及其他审批材料

模板可规定申请字段、活动时间地点、主办方、预算、附件清单和需要满足的通知条款。AI 仍然输出“哪些申请事实由哪些材料支持、与哪条要求冲突、还缺什么”。自定义任务允许用户从上传的依据生成字段与检查项，再人工确认，避免产品绑定单一学校的固定表格。

### 4.3 判断规则

可确定的数字、日期、必填项、上限和互斥关系应按可复查的规则核对；AI 处理材料语义，如活动简称、证书描述与指标名称是否同义。规则冲突时提示用户选定适用版本，不能自动选对申请人更有利的一份。只有规则分值明确、事项和证明能对应时才输出**建议分数**及计算依据；否则显示“待确认”。

结果类型包含：建议符合、建议补件、建议修改、需人工复核、未覆盖/未识别。每项结论都显示依据与材料出处、置信或不确定原因、下一步操作。看不清的印章、缺少的学号、未提供的官方记录不能被表述成“伪造”或“已通过”。没有校方历史数据时不声称跨案卷查重或已入账；未来接入后，若校方确实提供历史记录，才启用对应检查。

### 4.4 覆盖与历史

右栏摘要区分“已审核事项、待人工复核事项、未识别文件、规则未覆盖事项”。解析失败不从分母消失。用户修改依据、申报、证明或其关联后，原审核结果标为旧版本，新审核生成独立记录；人工决定与 AI 建议分别保留。案卷结果可导出为预审/复核报告，列出依据版本、事项、问题、引用位置、补件清单和人工处理记录。

## 5. 当前无校方 API 与未来接入：同一套案卷

学校没有提供审核 API 或页面，意味着现阶段无法确认真实字段、登录方式和审批状态。产品仍应把这些外部差异留在**案卷接入与状态回写层**，三栏只面对稳定的内部案卷。一个学校将来给 REST API，另一个只给 Excel 导出，或老师人工上传材料，三种来源映射成相同的内部对象；每个字段保留来源、原始值和更新时间。

| 能力 | 现在：独立运行 | 未来：校方接入 |
| --- | --- | --- |
| 用户身份 | 本地用户/演示角色，报告署名；不冒称已认证的老师。 | 学校 SSO 或授权账户，权限映射到学生、辅导员、审核员等角色。 |
| 规则来源 | 用户上传现行细则和通知，确认版本与适用学年。 | 从官方规则库读取或同步；仍允许本案补充临时通知，冲突需确认。 |
| 申请来源 | 上传申请表、证明或材料包，也可手工录入。 | 从申请系统拉取案卷与附件；原系统 ID 与内部 ID 建立映射。 |
| 审核历史 | 本工作台中的旧案卷、补件与审核记录。 | 可按授权读取学校历史申报/审批，用于重复计分和已入账检查。 |
| 决定与状态 | 生成 AI 建议和人工复核记录，导出/交接；不写学校状态。 | 授权审核人确认后回写学校系统，并读取回执与后续状态。 |

内部案卷需有稳定 ID、外部来源 ID、审核类型、申请人、学年、事项、证明、规则包、运行版本、人工决定和状态。每份依据、申请表、证明都保留来源位置：文件 ID 与版本、页/段落/单元格/图片区域，未来的外部附件 ID 也指向同一来源记录。这样换成校方接口后，问题卡的定位仍按内部来源位置工作。

外部接入必须容纳**缺字段、不同表格、附件后到、规则更新和状态不同步**：缺字段由界面提示和人工补充；外部状态不直接覆盖工作台的 AI 结果；校方回写成功以接口回执为准，失败则保留待同步状态；校方已经作出的正式决定优先展示，并保留此前 AI 和人工记录供追溯。未来校方 API 细节尚未知，本设计只固定内部语义与接入边界，不猜测其具体 URL 或审批字段。

### 接入边界需要固定的契约

| 边界 | 进入/离开工作台的最少信息 | 对三栏的保证 |
| --- | --- | --- |
| 案卷来源 | 来源类型、外部案卷 ID、申请人标识、审核类型、学年、原始状态、事项和附件引用、来源版本 | 无论由文件导入还是校方系统读取，都形成同一种可编辑的内部案卷；外部原值不因 AI 提取而被覆盖。 |
| 依据来源 | 规则文件或条款、发布单位、适用范围、版本、原文位置 | 左栏总能说明规则来自哪里；更换依据版本会触发重审，旧结论保留其原依据。 |
| 身份与权限 | 当前用户身份、可见案卷范围、允许的人工动作 | 同一界面按权限开放补件、复核和提交；没有校方认证时不能生成正式校方决定。 |
| 决定回写与状态读取 | 外部案卷 ID、材料版本、人工操作者、决定及理由；校方回执 ID、实际状态和更新时间 | 右栏区分“本地已确认”“待回写”“校方已接收”“回写失败”；外部状态变化不篡改既有 AI 发现。 |

校方系统若只提供部分能力，就只启用对应接入项。例如只给申请导出时，工作台仍用本地依据和人工报告；只给规则接口时，申报仍可上传。接入的验收方式是：同一份申报与依据从本地文件和校方来源进入后，能形成相同的事项、规则引用和问题卡，差别仅在来源标记与正式状态能力。

## 6. 案卷与审核流程的产品语义

| 概念 | 必须记录的内容 | 作用 |
| --- | --- | --- |
| 审核任务/案卷 | 类型、申请人、学年、来源、状态、规则包 | 把同一人的一批申报和证明组织起来 |
| 审核依据/规则 | 原文、适用范围、条件、分值/材料要求、版本、出处 | 使结论可核对、可替换规则版本 |
| 申报事项 | 原始字段、AI 提取字段、人工修正值、申报位置 | 一项一项审核，而非只评论整份文件 |
| 证明 | 原文件、可识别事实、所在区域、关联事项、识别状态 | 支持多图、多项及补件 |
| 问题/审核发现 | 类型、严重度、引用的规则与事项/证明位置、建议操作 | 驱动三栏联动和人工复核 |
| 审核运行与决定 | 输入版本、逐项结果、覆盖、建议分、人工动作及操作者 | 重审后仍能解释旧结果为何不同 |

流程允许草稿、已提交、AI 已审核、待补件、退回修改、人工复核、人工通过/驳回等状态。当前独立运行中，“人工通过”仅代表工作台内的复核记录；连接学校后，是否构成正式通过由校方权限与回执决定。学生补件会产生新材料版本和新一轮审核，旧问题与处理记录保留。

## 7. 输入与失败时的体验

目标输入包括文本型或扫描型 PDF、DOCX、XLSX/CSV、PNG/JPG 证明和材料包。界面按文件展示“已识别 / 部分识别 / 无法识别”，并允许打开原件、录入缺失字段或重新关联材料。自动识别不应依赖某一固定申请模板；模板用于提升准确性，用户确认后的事项才进入可靠的规则核对。图片/扫描件的 OCR 或视觉识别看不清时，系统要把相关事项留在人工复核列表。

文件名、页码、表格单元格和图片区域都可能成为问题卡的定位点。上传格式可逐步扩展，但文件无法解析时仍应保留原件和失败原因，不生成看似精确的假位置。对外部系统同步的材料也适用同一规则：拿不到附件原文时，只能定位到字段或附件记录，并在界面说明。

## 8. 主项目的真实现状与局限

| 已有能力 | 源码位置与局限 |
| --- | --- |
| Electron 主进程、preload IPC、React/Jotai 和多 Tab | apps/electron/src/main/ipc.ts、src/preload/index.ts、src/renderer/components/tabs/MainArea.tsx 可承载新工作台；目前没有审核案卷、三栏联动或角色工作流。 |
| 文档解析和预览 | apps/electron/src/main/lib/document-parser.ts、file-preview-service.ts 已能处理部分 PDF/Office/文本；当前提取内容偏纯文本，缺少可靠的单元格、页内区域及证明图片定位。 |
| 本地知识库与附件 | knowledge-item-service.ts、attachment-service.ts 可供文件和片段读取；知识库没有综测规则的学年、类别、分值、互斥和来源版本语义，附件也没有证明归属。 |
| 模型接口 | 现有 OpenAI 兼容图像消息路径可参考；项目仍有 Chat/Agent 双模式、Claude/Pi 运行时和多厂商渠道。它尚未满足全局的接口收敛目标。 |
| CDUTServer | 当前内容是校园访问相关脚本，不是综测规则库、学生申请库或学校审核服务。 |

关键缺口是一整条“材料 → 可审核事项 → 规则与证据对齐 → 可定位问题 → 人工处理”的产品链。单纯增加一个三栏页面或让模型生成整段点评都不能覆盖它。

## 9. 从 CDUT-Studio 基座开工的落点

这部分是对**当前源码**的复核，不把项目已有能力写成待重建模块。审核专区需要独立业务逻辑，同时使用现有桌面壳、文件能力、模型配置和组件体系。

| 现成基座 | 可直接复用 | 本区必须补的部分与原因 |
| --- | --- | --- |
| 主区与导航：renderer/atoms/active-view.ts、components/tabs/MainArea.tsx、app-shell/left-sidebar/ | 现有全屏视图切换、侧栏入口、窗口控件和主题布局。 | 内容审核作为一个新主视图，工作台内部自己管理三栏和案卷切换。当前 TabType 只有 Chat/Agent/预览/浏览器等，预览 Tab 还绑定会话；直接把三栏拆成三个 Tab 会破坏同步定位。侧栏展开态与窄轨各有入口，需同时接入。 |
| 状态与组件：Jotai、@profer/ui、Radix、现有按钮/弹窗/面板 | 当前案卷、选中问题、三栏定位、助手抽屉用 Jotai；沿用项目主题和已有组件。 | 审核数据由案卷文件持久化，Jotai 只保存当前界面状态，避免与资料原件产生第二份事实。 |
| 文件选择与附件：main/lib/attachment-service.ts | 文件类型/MIME、系统选择框和图片读取的现有经验。 | saveAttachment 按 conversationId 存储，openFileDialog 对小文件返回 base64，不能直接充当多文件案卷库；本区用案卷 ID 保存原件与版本，选择后在主进程受控导入。现有过滤器未列 ZIP，材料包需要单独覆盖。 |
| 解析：main/lib/document-parser.ts | PDF、Office、文本的已有纯文本提取能力；优先复用其格式处理。 | 审核还需带页、段落、表格单元格或图像区域的结构化块；仅有一整段文字无法完成双侧高亮。扫描图像需 OCR/视觉识别及“看不清”状态。 |
| 预览：main/lib/file-preview-service.ts、renderer/components/file-browser/FilePreviewDialog.tsx | PDF/Office/图片/文本的预览与“打开原件”能力，可作为失败回退。 | FilePreviewDialog 是弹窗，PDF 预览主要在 iframe 内画 canvas；它们没有对外的双侧滚动/定位接口。工作台要用相同文件读取能力构建可定位的内嵌来源视图，不能假设现有弹窗会自动高亮。 |
| 知识库：main/lib/knowledge-item-service.ts | 本地原件副本、提取文本与片段检索机制可供共享。 | 校规需学年、优先级、条件、分值和原文锚点；普通知识条目不能直接当审核规则包。可引用同一资料，但规则包要有独立结构与版本。 |
| 模型：packages/core/src/providers/openai-adapter.ts、main/lib/channel-manager.ts | OpenAI 兼容请求/图像格式及渠道凭据管理。 | chat-service.ts 与对话历史、消息持久化紧耦合，不能把一次案卷审核伪装成普通 Chat 消息。审核调用统一模型出口，自己管理结构化结果、引用校验、重审和失败状态。 |
| 本地配置：main/lib/config-paths.ts | getConfigDir() 的开发/正式环境隔离与配置文件习惯。 | 案卷原件、规则包、运行结果在其下按案卷 ID 独立存储；不另起本地数据库，也不放进聊天附件目录。 |

本区的最小新增边界是：shared 中的案卷/出处/结果类型与 IPC 名称，main/lib 中的案卷保存、材料结构化和审核服务，preload 的类型安全桥接，renderer 中的审核工作台与 Jotai 状态。主进程负责读取本地原件、模型调用与持久化；renderer 负责确认、展示和三栏定位。与主项目现有 IPC 路径一致，避免在页面里直接访问磁盘或模型密钥。

### 开工时先固定的四个内部契约

1. **SourceDocument**：文件 ID、版本/哈希、来源（上传或校方）、解析状态，以及带稳定 ID 的文本块、页码、表格 sheet/cell、图片矩形。左中预览与问题卡都消费同一锚点，不能各生成一套位置编号。
2. **ReviewCase**：案卷 ID、类型、申请人、学年、规则包、事项、证明、各字段的原始值/AI 值/人工值及来源。未来校方 API 只需映射到此结构。
3. **ReviewRun/Finding**：输入版本、已覆盖与未覆盖对象、规则锚点、申报/证明锚点、问题类型、红黄程度、建议操作和运行状态。右栏只能展示有核验来源的确定性结论；部分失败必须可见。
4. **ModelTask**：统一模型配置下的文本/图像输入、结构化输出、取消与错误；审核业务定义提示词和 schema，模型选择、凭据、OpenAI 兼容或本地私有通信由共享出口负责。

上述是模块之间需要稳定的输入输出，不限定具体文件名或类名。它们能先支持本地样例，之后接入校方系统、替换预览实现或调整模型时仍保持案卷与问题卡语义。

## 12. 模型通信与全局接缝

产品全局目标是只保留**OpenAI 兼容通信接口**，并为本地模型平台提供**单独的私有接口**。审核专区只面向这两个模型出口，不新增 Claude、Google 等厂商专用协议。文件和校方系统接入属于案卷来源，与模型通信分开；将来学校换接口不应迫使规则提取、问题卡或助手重写。当前主项目尚未完成旧厂商渠道清理，此项需与负责第 1、2 区及全局配置的成员统一验收。

## 13. 验收结果

完整产品需要在综测和活动材料两类案卷中，完成规则导入、申报与证明识别、人工修正、逐项预审、双侧原文定位、补件重审、审核助手、人工处理及报告交接；有校方接口时，还应完成身份授权、案卷/规则同步与正式结果回写。没有校方接口时，上述案卷内审核能力照样成立，正式学校审批显示为“未连接”。

明天的演示应覆盖**完整的一次审核流程**，而不是静态页面：打开或上传一份标明模拟的规则与申请材料，看到规则大纲、申报事项与证明绑定；右栏同时出现明确冲突和证据不足的卡片；点击卡片发生真实的左中定位与蓝/红/黄高亮；修正或补件后重审；向助手追问；最后查看可交接的预审结果。活动材料可用第二份模拟案卷展示同一工作台可换规则与字段。演示使用模拟案卷，不意味着最终功能缩减；校方接入能力以预留的案卷来源、权限和状态边界评审，待取得真实接口后完成联调。
